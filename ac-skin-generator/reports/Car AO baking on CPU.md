# Bake car AO on CPU with numpy

Bake the AO by copying what Content Manager (CM) does, with a cheaper visibility test. Take about 256 fixed sky directions. For each direction, build one orthographic depth map of the whole car. Then, for every UV texel, test its 3D point against that map and average max(n.l, 0) x visibility over the directions. CM's "Baked shadows" does exactly this on the GPU, with 5000 lights by default and a 2048 px shadow map per light, and then applies `clip((mean x 2.2)^0.6, 0, 1)`. A numpy version should splat a dense point cloud into each depth map with `np.minimum.at` (measured at 0.05 s for 8 M points on 1024^2, so roughly 30-60 s for 256 directions, an untested estimate). Bake at 1024 or 2048, fill the gutters with pull-push, upsample, re-mask, and use the result as `livery x (1 - s(1 - ao))` with s of about 0.4-0.7. No source documents this exact numpy pipeline end to end. The numbers below are CM's real values where cited, and my derivations or judgement where marked.

## CM bakes by summing hundreds of shadow-mapped lights in UV space

CM has two bakers, and only "Baked shadows" (`BakedShadowsRenderer.cs`, with the `Ao` technique in `SpecialShadow.fx`) writes a texture-space AO. The other, "Ambient shadows", makes a top-down ground shadow (`body_shadow.png`) and is irrelevant here ([BakedShadowsRenderer.cs](https://github.com/gro-ove/actools/blob/master/AcTools.Render/Kn5SpecificSpecial/BakedShadowsRenderer.cs), [SpecialShadow.fx](https://github.com/gro-ove/actools/blob/master/AcTools.Render/Shaders/Special/SpecialShadow.fx)). The author describes it as hundreds or thousands of randomly distributed sky lights, each with a shadow map, summed up ([tip text](https://github.com/gro-ove/actools/blob/master/AcManager/About/ImportantTips/Custom%20Showroom%20Shadows%20Baking.txt)).

The UI defaults are listed in the table below ([ViewModel](https://github.com/gro-ove/actools/blob/master/AcManager/CustomShowroom/BakedShadowsRendererViewModel.cs)).

| Parameter | CM UI default | Meaning |
|---|---|---|
| Elevation range | 0 to 60 deg | Light directions, Poisson-sampled uniformly in sin(elevation) with uniform azimuth. 0 to 90 is the full hemisphere; -90 to 90 is all around, for wheels. |
| Iterations | 5000 (class default 500) | Number of lights |
| Shadow map | 2048, orthographic, width = car bounding-box diagonal | About 2.5-3 mm per texel |
| Bias | 0 (front faces) / 0.7 (back faces) | Raster depth and slope bias; both faces are drawn into the same map |
| Ambient | 0 | Fake ground bounce: `saturate(y*2)*Ambient` is mixed into the light term |
| Brightness / Gamma | 2.2 / 0.6 | `out = clip((mean(light x shadow) x Brightness)^Gamma, 0, 1)` |
| Padding | 4 iterations of the grow filter | Island dilation |
| Pixel density | 4 (2x2 supersampling) | Bake at 2x, then downsample |

Per texel, CM computes `light = saturate(n.l)` using the normal-map normal, multiplies it by a 2x2 PCF shadow lookup of the texel's world position, and sums over the lights. Nothing in the baked scene is a ground plane. Glass with alpha above the reference value still occludes; the depth pass only alpha-clips non-opaque or alpha-tested materials. There is no normal offset either. Self-shadowing is controlled only by the depth bias and by drawing both faces.

My arithmetic, not checked against a real CM output: an open, upward-facing texel gives a mean n.l of 0.433 over 0-60 degrees, so 0.433 x 2.2 gives 0.95, and ^0.6 gives 0.97. Vertical sides come out lower, and undersides come out near 0 unless Ambient is above 0. I found no evidence that CM's paint shop uses or multiplies an AO map. CM only saves the map as a file for mods that lack one.

## A fixed direction set with per-texel cosine weights replaces per-ray sampling

GPU Gems ch.17 asks for 128-1024 lights uniformly distributed on the sphere (not on a lat/long grid), accumulated in float, and says a hemisphere is enough for an object standing on a plane ([GPU Gems 17](https://developer.nvidia.com/gpugems/gpugems/part-iii-materials/chapter-17-ambient-occlusion)). Substance's default is 64 rays with cosine distribution ([Substance AO](https://experienceleague.adobe.com/en/docs/substance-3d/bakers/bakers-settings/ambient-occlusion-from-mesh)). Because depth maps are shared by all texels, per-normal cosine rays are impossible. My recommendation is a Fibonacci set of directions with weights w = max(n.d, 0), and AO = sum(w V) / sum(w) over the same set. Use N = 256 for the final bake and 64-128 for a preview, and skip directions where n.d is below about 0.05. Fixed directions give banding rather than noise, with about 12.6 deg spacing at N = 256. A light edge-aware blur (see the pipeline section) hides it, and CM's 5000 lights would not be affordable on the CPU.

Use the upper hemisphere for the body. CM's default 0-60 degree cap is mainly a style choice, but it also keeps the roof bright. Use -90 to 90 only for wheels and arches. Instead of CM's fake Ambient term, add a ground occluder at tyre-contact height if you want dark sills. Weight below-horizon directions at about 0.5 so the sills do not go black. That is my judgement, not a sourced recipe.

For the depth maps, use one fixed bounding sphere (radius about 2.8 m for a 4.5 m car) so the pixel size p = 2R/res is the same in every direction. Use 1024 px (about 5.5 mm) for previews and 2048 px (about 2.8 mm, the same as CM) for finals. A texel is lit when its depth is at most the map depth plus a bias. The bias is my derivation, not sourced: 1.5-2 p plus p x min(tan theta, 5), together with a normal offset of 1-2 p along the texel's normal before projecting. At p of about 5 mm that is a bias of 8-10 mm and an offset of 5-10 mm. Larger values only lighten gaps narrower than about 1 cm, which is acceptable for a skin. Take the occluders from every opaque body panel, wheels, brakes, mirrors and exhaust. Drop glass, shadow planes, light cones, decal and dirt copies lying on panels, and the driver, or a coplanar duplicate will shadow its twin. Both faces of thin shells occlude automatically when you splat points.

## Splat a dense point cloud instead of rasterising triangles

I measured this on numpy 2.5.4 (script `D:\ClaudeData\tmp\bench_zb.py`). Splatting 8 M random points into a 1024^2 float32 buffer with `np.minimum.at` took 0.05 s, against 0.21 s for a packed-int64 sort, 0.77 s for argsort with last-wins assignment, and 3.49 s for lexsort. The old advice to avoid `ufunc.at` ([numpy #5922](https://github.com/numpy/numpy/issues/5922)) was true on old numpy but has been fixed. Real projected points are more spatially coherent than my random test, so they should be no slower, but I did not test that. True triangle rasterisation in numpy is irregular and slower, so splatting is the better choice.

Generate the cloud once, as stratified barycentric samples per triangle, and reuse it for every direction. Use a spacing of at most 0.5 p, which is about 2.5 mm. That gives roughly 4-6.5 M points for 25-40 m2 of surface, plus the vertices and centroid for tiny triangles. The spacing keeps surfaces tilted to about 60 deg from the view direction free of holes, because projected density falls with cos(theta). For each direction, project the points and `np.minimum.at` them into an +inf float32 buffer. Apply a 3x3 min filter (np.minimum over 9 shifted views) to close grazing-sliver holes. It acts like a conservative extra pixel of bias. Then project the texel points (offset along their normals) and compare. Keep a per-texel 3D position and normal map, built once from the UV-space rasterisation of the mesh, because the blur and the visibility test both need it.

## Bake at low resolution, fill gutters by pull-push, then upsample

AO is low-frequency, so a 1024 or 2048 bake upsampled to 4096 is fine on open panels. The risks are island rims and sharp creases. No source documents upsampling an AO bake directly, so the order below is my inference. The dilation facts come from Blender, Substance and Polycount sources.

1. Blur inside the islands with normalised convolution, which means blurring (AO x mask) and mask with the same Gaussian and then dividing. Make it bilateral on world normal or position, using the texel-to-3D map. Unity's AO bake does the same kind of edge-preserving filtering, with sigmaPos 2, sigmaValue 0.2 and sigmaNormal 0.2 ([Unity](https://docs.unity.com/en-us/asset-transformer-sdk/2026.4/manual/functions/bakeao.md)). Radius is about 1-2 % of the bake width (my estimate).
2. Erode the coverage mask by 1 texel before filling, so partial-coverage rim texels that average island data with empty texels cannot make dark seams.
3. Fill every empty gutter texel with pull-push, equivalent to Substance's "dilation infinite". Blender's guidance is at least 1 px of margin per mip level, so 16 px covers the base plus three mips ([Blender bf-committers 2013](https://archive.blender.org/lists/bf-committers/2013-February/039281.html)). A full fill never runs out of padding. Pull-push (Gortler et al. 1996) builds a pyramid of 2x2 sums of colour x weight and weight, then pushes coarse data down into the holes ([Kraus 2009](https://www.cs.cit.tum.de/fileadmin/w00cfj/cg/Research/Publications/2009/Pull-Push_Algorithm/grapp09.pdf)). Use bilinear upsampling in the push and keep the original texels wherever coverage is 1. Pull-push gives a smoother fill than nearest-neighbour dilation, but I found no authoritative source saying it is better for mipmaps; that is my reasoning.
4. Upsample bilinearly (or bicubically) to 4096, then re-mask with the 4096 coverage mask and run a final pull-push at 4096, so the gutters match the sharper full-resolution island edges. Normalised convolution (upsample colour x coverage and coverage separately, then divide) gives the same result without the pre-fill.

Blender's Extend margin is a pure image filter and avoids the interior bleed that "Adjacent Faces" can cause ([Blender #119393](https://projects.blender.org/blender/blender/issues/119393)), which supports using a pure image-space fill rather than a polygon-aware one. CM's own padding (4 iterations of a grow filter, at 2x resolution before the downsample) is much shorter than a full fill. A full fill is safer here.

## Turn AO into a multiplier that darkens only the occluded areas

Multiply is the standard blend for AO ([Substance Painter](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/painting/advanced-channel-painting/ambient-occlusion-painting)). One forum poster found multiply at 100 % dull in LFS and reduced the layer opacity ([LFS forum](https://www.lfs.net/forum/post/420439)). The formula below is my own, not from a source.

`shade = 1 - s x (1 - clip(ao / p95(ao), 0, 1)^g)`, then `out = livery x max(shade, floor)`, with s about 0.4-0.7, g about 1.5-2 and floor about 0.25.

Normalising by the 95th percentile (or the median of open panels) makes open panels about 1.0, so only creases, arches and gaps darken. The contrast curve g keeps mild occlusion near 1. The floor stops flat-black wraps and metallic areas from going darker still. Apply it to the diffuse only. If you reuse CM's output curve, remember it is an artistic curve, not linear AO: `(mean x 2.2)^0.6` is already brightened.

Several pitfalls remain. First, double darkening: stock Kunos cars reportedly ship a separate baked AO texture, but I could not find whether the AC car shader multiplies it into the final colour, so keep s modest and check against the kn5 shader if it matters. Second, colour space: multiplying directly on sRGB-encoded 8-bit values darkens more strongly than a linear multiply, so tune s by eye and stay consistent. Third, overlapping or mirrored UVs: for left/right mirrored parts, averaging the two AO values is fine because the car is nearly symmetric. For stacked islands (inner and outer door skins), prefer the outer surface, not an average. Fourth, single-sided panels whose back faces are open: ignore back-face hits, or the unfilled inside can darken the outside. Fifth, UV tiling: CM redraws the mesh for each integer UV tile from -10 to 10 and folds it into 0..1 with MAX blending, so texels that map to several surfaces take the lightest value (my reading of the code; I did not verify the V flip or handedness against a real output).

## Conclusion

The research supports a clear recipe. Use 256 fixed directions with cosine weights from the upper hemisphere, 2048 px orthographic depth maps, bias of about 1.5-2 pixel footprints plus a slope term and a normal offset, and a point-splat z-buffer built with `np.minimum.at`. Then run the blur, erode, pull-push, upsample and re-mask pipeline, and apply a 0.4-0.7 multiplier normalised to the 95th percentile. The one finding that changes the usual advice is that numpy's `ufunc.at` is now the fastest way to build a z-buffer, and a full CPU bake looks achievable in a minute or so.

Open items, all unverified: the end-to-end timing, the bias values on a real mesh, whether AC's car shader already multiplies in its own AO map, and CM's UV-tile handedness. I suggest comparing one panel against a CM-baked map and tuning the bias, s and g by eye on door seams, grille gaps and wheel arches.
