# Paint protected cars through their skin folders

The Ratty's4Skin Generator can give CSP-protected cars a real livery without going near the protection, because the protection hides the **model** and leaves the **skin folder** open. A plain reader of a protected kn5 on this PC still sees names, materials and geometry. Its UVs are scrambled (u values up to about ±280) and every embedded texture is a 1×1 placeholder. The DDS files in `skins\<skin>\`, by contrast, are ordinary images laid out on the real UV map the game uses. That makes a 2D "template" mode, painting the texture sheet panel by panel, both legitimate and the only practical route. Content Manager's template tools (View mapping, Calculate AO, Paint Shop) all live inside Custom Showroom, which by default does not load encrypted cars. The scale justifies the work. **153 of 846 installed car folders hold placeholder-only kn5s, and 38 more cannot be parsed at all, yet 100 of the 153 ship maker templates (AO, wireframe, PSD/PNG) in their skin folders.** Image-only panel recognition worked on the one layout tested, the unprotected Talbot. Run-based labelling, a mirror-axis test and a wheel-arch notch detector found the top view, both sides, the sill and the wheel positions. Front/rear and left/right still need one click from the user. The recommended design is a sealed code path, entered only when the existing detector already says "protected". It builds its island map from the best template source on disk, asks the user to confirm a labelled overlay, recolours with a shading ratio that keeps the baked AO, and writes only new skin folders. That should leave `same_output_cars.py` reporting IDENTICAL for every car that works today. The same layer-and-finish engine is also the way into iRacing, ACC, rFactor 2/LMU and AMS2. Those sims already paint only in 2D, but each wants different files.

## Protection scrambles the model and leaves the skin folder open

CSP's encrypter rewrites a car's kn5 to stop the model being edited or stolen. Encrypted models then load only in AC with CSP, or in Content Manager's Custom Showroom if the author arranges it. The documentation never lists which fields are encrypted, and the author is open that it is an imperfect, reluctant measure ([CUP docs: kn5 encryption](https://cup.acstuff.club/docs/csp/misc/kn5-encryption); [CSP wiki](https://github.com/ac-custom-shaders-patch/acc-extension-config/wiki/Misc-%E2%80%93-KN5-encryption)). A second mode ties the model to `data.acd`. That data stays readable and is only protected against changes, so writing new skin folders touches neither file ([CUP docs](https://cup.acstuff.club/docs/csp/misc/kn5-encryption)). This research deliberately did not look into how the protection works. What follows is only what a plain, read-only reader sees on this PC (CSP 0.3.1-preview2).

| Part of a protected kn5 (4 cars checked in depth) | What a plain reader gets | Use to the app |
|---|---|---|
| Header | normal `sc6969` magic, version 6 | detection |
| Material, shader, sampler and texture names; node and mesh names | plain, e.g. 51 materials on the Ferrari 296 GT3 | tells which skin file is the paint |
| Vertex positions and normals | car-sized bounding box, 100 % unit-length normals | not needed (not verified as the true shape) |
| UV channel | u −278..+279, v −43..+44; 88–90 % of triangles under 3 cm have UV corners more than a quarter of the texture apart (0–1 % on normal cars) | **off-limits** beyond detection |
| Embedded textures | 82–93 named entries, each a 70-byte 1×1 PNG, about 0.01 MB in all, against 118.8 MB of real DDS in the unprotected `ks_bmw_m4_gt3` | none |

Sources for the table: local scripts [peek.py](file:///D:/ClaudeData/tmp/csp_prot/peek.py), [sizes.py](file:///D:/ClaudeData/tmp/csp_prot/sizes.py) and [geom.py](file:///D:/ClaudeData/tmp/csp_prot/geom.py).

The skin folder tells the opposite story. The protected Ferrari 296 GT3's skin `2023_GTWC_14_Emil Frey Racing` holds `EXT_Skin_Colour.dds`, a **4096² uncompressed DDS of 89.5 MB**. It opens in Pillow as a normal livery sheet, with flat body panels, sponsor logos and the number 14, on the same layout as the maker's wireframe ([local preview](file:///D:/ClaudeData/tmp/csp_prot/cf_ferrari_296_gt3_EXT_Skin_Colour.dds.png); [skins.py](file:///D:/ClaudeData/tmp/csp_prot/skins.py)). Makers of protected cars know painters need this. The 296 ships four `Template*` skins, each with PSD, XCF, PNG and DDS copies of the body texture, a 4096² `Wireframe.png` of the UV layout in green lines, AO, a working `ext_config.ini` and a PDF guide. The guide says aero packages switch through Model replacements in the skin's `ext_config.ini`, and that the number-plate emissive texture uses the same mapping as the skin texture ([car folder](file:///D:/SteamLibrary/steamapps/common/assettocorsa/content/cars/cf_ferrari_296_gt3/); [wireframe thumbnail](file:///D:/ClaudeData/tmp/csp_prot/wire_296.png)). Across the install, 153 of the 846 car folders that have a kn5 hold only placeholder textures, and **100 of those 153 ship template-like files**: ADC drift cars, the GT4 pack (per-skin `EXT_BODY_AO.dds`), `supercars_gen3_*` and the `fsr_*` BTCC cars. Traffic cars, karts and several street cars ship none ([scan.py](file:///D:/ClaudeData/tmp/csp_prot/scan.py)).

Protection shows up in two forms. In state (a), 153 cars, the kn5 parses but has scrambled UVs and placeholder textures. In state (b), 38 cars (all 29 `rss_*`, 5 `gravygarage_*` and 4 others), the kn5 cannot be parsed past the header. Some of those 38 are simply 0-byte broken installs ([scan.py](file:///D:/ClaudeData/tmp/csp_prot/scan.py)). The app already detects both. `scrambled_uv()` measures the scrambled-triangle share, and `kn5.py` turns a parse failure into "protected (locked)". A protected car then gets a plain colour, and the app never tries to undo the protection ([skingen.py](file:///D:/Claude/Claude-/ac-skin-generator/skingen.py) lines 463–473; [kn5.py](file:///D:/Claude/Claude-/ac-skin-generator/kn5.py) line 45; [README](file:///D:/Claude/Claude-/ac-skin-generator/README.md) lines 211–214). A cheaper check would be to flag a car when every texture entry in the kn5 is 100 bytes or less. It needs no geometry at all, and it agreed with `scrambled_uv` on all four cars tested in depth.

On legitimacy, nothing official addresses liveries for encrypted cars, so the position has to be inferred. The CSP author asks people not to encrypt Kunos's or others' content without permission, to keep encrypters private and to think twice about encrypting at all. He values AC's openness and aims the protection at re-releasers of models ([CSP wiki](https://github.com/ac-custom-shaders-patch/acc-extension-config/wiki/Misc-%E2%80%93-KN5-encryption)). Reading the plain skin-folder textures and the visible material names, then writing new skin folders, is exactly what every human painter does, so it sits inside the intended use. Reading or rebuilding the scrambled UVs, using the kn5's texture data, or capturing GPU data would cut against both the stated purpose and the author's request. Painters do report the practical cost. One GTPlanet modder painted an encrypted car without proper AO mapping, and another asked for an unencrypted copy just to get the AO; both come from search snippets only and could not be checked ([GTPlanet post 14594330](https://www.gtplanet.net/forum/threads/assetto-corsa-pc-mods-general-discussion.307899/post-14594330)). One more sanctioned route exists in principle. CSP's in-game Paintshop app (CSP 0.1.77 or later) paints on the car in game and exports a texture, using the original texture as AO, but nobody has confirmed it works on encrypted cars ([app-paintshop](https://github.com/ac-custom-shaders-patch/app-paintshop)).

## Content Manager's template tools stop at the showroom door

Content Manager's source code (actools, with commits as recent as June 2026) shows what a painter normally gets from the "Car texture" dialog in Custom Showroom ([commits](https://github.com/gro-ove/actools/commits/master)). There are four buttons, and only two of them make templates.

| Button | What it produces | Format and defaults | On a protected car |
|---|---|---|---|
| View mapping | UV0 wireframe of every mesh that uses the texture, with UVs outside 0–1 wrapped back into the square | **pure #00FF00 antialiased lines on a fully transparent background**, at the texture's own size (or 512–4096/custom); saved as PNG, DDS or JPEG | unavailable |
| Calculate AO | grayscale ambient-occlusion bake projected onto that texture's UV layout | texture size by default; 5000 iterations, 4 px padding, DXT5 for DDS | unavailable |
| Export | raw texture bytes from the kn5 | only in Developer mode, and only for an editable kn5 | unavailable (placeholders anyway) |
| Replace | writes a new texture into the kn5 itself | modelling tool, not skinning | never use |

Sources for the table: [Kn5TextureDialog.xaml.cs](https://github.com/gro-ove/actools/blob/master/AcManager/CustomShowroom/Kn5TextureDialog.xaml.cs), [UvRenderer.cs](https://github.com/gro-ove/actools/blob/master/AcTools.Render/Kn5SpecificSpecial/UvRenderer.cs), [SpecialUv.fx](https://github.com/gro-ove/actools/blob/master/AcTools.Render/Shaders/Special/SpecialUv.fx), [BakedShadowsRendererViewModel.cs](https://github.com/gro-ove/actools/blob/master/AcManager/CustomShowroom/BakedShadowsRendererViewModel.cs).

None of this reaches protected cars. CSP's own documentation says encrypted cars will not work in Custom Showroom by default. An author can either ask for CM support, accepting a warning that it adds a theft route, or ship a deliberately simplified, unencrypted stand-in model under `[LOD_HR]` in `lods.ini`, which AC ignores and CM shows instead ([CUP docs](https://cup.acstuff.club/docs/csp/misc/kn5-encryption)). Of all the encrypter versions, only the old basic one, now described as broken, supported the showroom ([CUP: about old encryption](https://cup.acstuff.club/docs/about-old-encryption)). A CM changelog line says Custom Showroom no longer opens encrypted models it cannot decrypt, but it was seen only in a search snippet ([CM changelog](https://acstuff.club/f/d/10-content-manager-detailed-changelog/273)). CM's kn5 reader also rejects any file without the standard signature ([Kn5Basic.cs](https://github.com/gro-ove/actools/blob/master/AcTools/Kn5File/Kn5Basic.cs)). Paint Shop itself runs inside the showroom ([LiteShowroomTools.PaintShop.cs](https://github.com/gro-ove/actools/blob/master/AcManager/CustomShowroom/LiteShowroomTools.PaintShop.cs)). None of this was tried hands-on in CM; it comes from reading the source.

Paint Shop's rule file is a different matter: it is plain text and fully usable. `ui/cm_paintshop.json` names each paintable texture and its kind (`color`, `carPaint`, `pattern`, `licensePlate`, `tintedWindow`, replacements), with default colours, R/G/B masks for colours 1–3, and **number, name and flag positions in texture pixels**. Resources prefixed `./` are loose files in `ui/cm_paintshop/` ([CM Paint Shop manual, 2017](https://acstuff.club/f/d/16-content-manager-paint-shop); [PaintShop.cs](https://github.com/gro-ove/actools/blob/master/AcManager/PaintShop/PaintShop.cs)). On this PC, 55 cars carry one. `rss_formula_1990`, for example, puts a number box at pixel (512, 777), size 275, over a loose `./90_Masters.dds` underlay ([local file](file:///D:/SteamLibrary/steamapps/common/assettocorsa/content/cars/rss_formula_1990/ui/cm_paintshop.json)). The files are not strict JSON. They have trailing commas, bare top-level arrays, keys belonging to a different car ID, and type names in mixed case. A parser has to be lenient. On a protected car, entries that point to textures inside the kn5 still give names and defaults, but their pixels are out of reach.

The lesson for the app is to **consume CM-format template files when a maker ships them**, not to copy CM's bake. The 296's `Wireframe.png`, green lines on a 4096² RGBA canvas, matches CM's View mapping output, so a detector tuned to "#00FF00 lines on transparent" and "near-grayscale AO" will recognise most maker templates. An author-shipped `[LOD_HR]` model is the one case where CM's own route still works. It is unencrypted on purpose, but its UVs are only as faithful as the author made them, and no list of cars that ship one exists.

## Four other sims already paint in 2D, each with its own file contract

For iRacing, ACC, rFactor 2/LMU and AMS2, a third-party tool works from the 2D templates and uses each sim's own showroom as the 3D check. Studio 397's own rF2 cars are encrypted (community reports), AMS2 overrides work without extracting any game files, and nothing found suggests the other sims' car models are meant to be read ([OverTake: rF2 HDV files](https://www.overtake.gg/threads/rfactor-2-hdv-files.182237/), snippet; [Reiza forum](https://forum.reizastudios.com/threads/ams2-user-livery-overrides.14819/)). Extraction was deliberately not researched.

| Sim | Paint output | Size | How finishes are set | Folder and sharing |
|---|---|---|---|---|
| iRacing | `car_<customerID>.tga` (sim stamps the number) or `car_num_<customerID>.tga` (own numbers); 24-bit, no stray alpha | 2048² (1024 accepted) per a **2015** PDF | `car_spec_<id>.tga`: R metallic, G roughness, B clear coat (white), A specular mask; the sim builds a `.mip` | `Documents\iRacing\paint\<car>\`; others see it only via Trading Paints |
| ACC | `decals.png` + `sponsors.png`, transparent RGBA over the in-game base paint | decals ≤ 2048², sponsors ≤ 4096² | `decals.json` / `sponsors.json`: `baseRoughness`, `clearCoat`, `clearCoatRoughness`, `metallic` (two finishes at most) | `Customs\Liveries\<customSkinName>\` + car json in `Customs\Cars\`; local only |
| rFactor 2 | `alt_<name>.dds` DXT5 (alpha = carbon specular only), name ≤ 12 characters | not stated | `alt_<name>_Region.dds`: flat Black/Red/Green/Blue/White/Alpha regions with exact template RGB, materials chosen in the showroom; **no baked AO** | `UserData\player\Settings\<car>\<team>\`; sent to other drivers automatically as `.mas` |

| AMS2 | DDS replacing an **existing** livery slot, plus a per-car XML (`LIVERY`, `NAME`, `BASELIVERY`, `BODY`) | reportedly 4096² | DXT1/DXT5 depending on base finish (forum reports) | `Vehicles\Textures\CustomLiveries\Overrides\`; local only |

Sources for the table: [iRacing paint textures](https://www.iracing.com/painttextures/), [iRacing 2015 PDF](https://ir-core-sites.iracing.com/members/pdfs/2015_01_20_custom_paint_schemes.pdf), [Trading Paints spec map help](https://help.tradingpaints.com/painting/how-do-i-create-a-spec-map-file-for-use-in-iracing/), [get-good ACC wiki, 2021](https://www.get-good.net/index.php/Getting_Skins_Into_Assetto_Corsa_Competizione), [True2Life ACC guide](https://overtake.gg/threads/true2life-racing-how-to-full-custom-liveries-in-assetto-corsa-competizione.183706/), [S397 material-system guide, Jan 2023](https://docs.studio-397.com/x/lwAqBQ), [RaceControl LMU guide, Jul 2025](https://news.racecontrol.gg/?p=1223), [LMU v1.1 news, Sep 2025](https://lemansultimate.com/lmu-adds-first-elms-content-and-custom-livery-upgrades/), [Reiza overrides thread](https://forum.reizastudios.com/threads/ams2-user-livery-overrides.14819/), [Reiza forum post](https://forum.reizastudios.com/goto/post?id=316450).

Several of these sources are dated, so treat the details as provisional. iRacing's sizes come from a 2015 PDF, and the ACC details from a 2021 wiki. LMU's September 2025 v1.1 notes add offline and hosted-server use, which contradicts the July 2025 guide. The AMS2 details are forum anecdotes, and the authoritative XML schema is the `_dist.xml` shipped in the user's own Overrides folder. The templates follow one pattern across all of them: paint layers sit at the bottom, and above them are guide layers (wireframe, masks, stamped logos, number-plate positions, carbon areas) that are switched off before export. iRacing groups these under "Turn Off Before Exporting TGA", and LMU's Mask layer must be disabled while its Levels layer stays on ([Trading Paints painting guides](https://help.tradingpaints.com/paint-builder/using-paint-builders-painting-guides/); [RaceControl](https://news.racecontrol.gg/?p=1223)). Two traps matter for an exporter. A stray alpha channel can make an iRacing paint vanish ([Trading Paints troubleshooting](https://help.tradingpaints.com/downloader/troubleshooting-all-black-custom-paints/)). And rF2 wants albedo with no baked AO, because the engine applies AO itself ([S397](https://docs.studio-397.com/x/lwAqBQ)).

That last rule shapes the AC design too. AC skins carry baked shading in the diffuse, while rF2 must not. The 2D engine should therefore hold **paint (T) and shading (S) as separate layers** and multiply them only at export, for the sims that want it. The guide layers become "no-paint zones". Every sim also needs a per-layer finish (gloss, matte, metallic, chrome, carbon) that exports differently: as iRacing spec channels, as ACC json floats, or as rF2/LMU region colours.

## Image-only panel recognition works, with one click of human help

No livery tool or paper found recognises car panels from the flat texture image. Blender computes UV islands from mesh connectivity ([bf-blender-cvs, 2022](https://lists.blender.org/pipermail/bf-blender-cvs/2022-May/173582.html)), LiveryHelper mirrors decals using the 3D model ([Livery Helper](https://extensions.blender.org/add-ons/livery-helper/)), and BeamNG and flight-sim painters work by eye over a layout screenshot or a layered kit ([BeamNG skin tutorial](https://documentation.beamng.com/modding/materials/vehicle/skinsystem/skintutorial)). The pipeline below is therefore new ground. It was validated only by read-only probes on three skins of the **unprotected** Talbot Sunbeam ([uvseg_probe.py](file:///D:/ClaudeData/tmp/uvseg_test/uvseg_probe.py); [uvseg_probe2.py](file:///D:/ClaudeData/tmp/uvseg_test/uvseg_probe2.py)). The probes use numpy and Pillow only.

### Masks must come from templates, not from the skin being painted

The app already contains a numpy run-based labeller. `enclosed()` finds row runs with `np.diff`, links overlapping runs with two `searchsorted` calls, and merges labels with `np.minimum.at` plus pointer jumping ([skingen.py](file:///D:/Claude/Claude-/ac-skin-generator/skingen.py) lines 559–590). This is the standard run-length plus union-find family of connected-component labelling ([MDPI Algorithms 18(6):344](https://www.mdpi.com/1999-4893/18/6/344)). The probe generalised it to an 8-connected `label()` with a one-pixel overlap pad. It **labelled a 2048² texture and measured 18 islands in 0.4–0.6 s**. The background is the modal colour of the one-pixel border, and it is not always black: (0,0,0) on `CRT-Kris`, (36,36,36) on `MessDraw #16`. Both skins showed exactly 60.8 % background, which means identical UV coverage. With a threshold of 10 and a one-pixel close-then-open, `CRT-Kris` went from 60 raw components to 32, ten of them large. Per-island hole filling then closed the gaps left by black lettering, 18,815 px in each side island ([CRT-Kris labels](file:///D:/ClaudeData/tmp/uvseg_test/CRT-Kris_labels.png)). The method **breaks on dark liveries**. On the mostly black `ratty_s`, 83.7 % of pixels match the background, and the result shattered into 359 components with no clean side. So the mask should come, in order of preference, from a maker AO or wireframe, then from the union of the masks of every installed skin (the Talbot has 13), then from the lightest stock skin, and only last from the skin being edited. Two masks are worth keeping: raw coverage for measuring, and hole-filled coverage for painting. Thresholds belong on the decoded DDS before any resizing. DXT blocks measurably raise the gradient at 4-px block edges (1.15–1.34×), and a 2-px close would merge strips that sit 2–4 px apart.

### Mirror symmetry and wheel arches identify the panels

Three shape cues identified the Talbot's panels without error. First, the whole foreground mirrors about a horizontal axis at y = 1031.0 with IoU 0.87–0.90. Second, the two side islands match after a vertical flip at **IoU 0.93–0.99** (0.88 even on the black `ratty_s`), against 0.31–0.49 unflipped. Their PCA angles are equal and opposite (±3–4°), and their seventh Hu invariant has opposite signs. That is expected, because I7 is the one Hu invariant that changes sign under reflection ([Wikipedia: Image moment](https://en.wikipedia.org/wiki/Image_moment)). Third, a notch detector found **exactly two wheel-arch notches** on the edge of each side island that faces the axis, and none anywhere else. Those notches mark the sill and give the wheel centres in texture space. The top view (bonnet, roof and hatch) is the largest island that is self-symmetric about the axis. Front versus rear could not be decided: the overhangs were 120 and 148 px, and profile skew was ±0.05. Left versus right cannot be decided either, because the sides are exact mirrors. The honest design is to guess, show the guess, and let the user confirm it with one click, then store the answer per car. When the mirror axis is weak, for example with sides packed next to each other or rotated 90°, pair matching across all four flips is the fallback.

### A shading ratio recolours without losing the baked AO

The recommended recolour works out a per-pixel shading factor `S = Lum(pixel) / Lum(ref)`, with `ref` set to the 75th percentile of the panel's luminance. The output is `T × min(S, 1)`, with a screen-like roll-off where S > 1 so highlights survive. On a white stock car this is exactly Multiply. On a mid-grey car it behaves like Overlay. Because only luminance enters S, the old hue never leaks into the shadows. The obvious alternatives fail in a predictable way. W3C/Photoshop "Color" mode keeps the base's luminance ([W3C Compositing Level 1](https://www.w3.org/TR/compositing-1/); [Wikipedia: Blend modes](https://en.wikipedia.org/wiki/Blend_modes)), and so does GIMP Colorize, which rebuilds HSL lightness from the base ([GIMP colorize source](https://sources.debian.org/src/gimp/2.8.18-1%2Bdeb9u1/app/gegl/gimpoperationcolorize.c)). Both turn navy on a white car into light blue. Dark base paint is the hard case. DXT stores endpoints as 5:6:5 bits ([Wikipedia: S3TC](https://en.wikipedia.org/wiki/S3_Texture_Compression)), so stretching a near-black panel to a bright target magnifies banding. The fix is to take S from an AO bake, or else blur S and cap it at about 1.5. Old logos in the base skin "ghost" through the new colour. Pixels where S drops below about 0.35, or where the chroma departs from the panel median, should be refilled from their neighbourhood, or the app should warn that the base is not a clean template. How AC blends diffuse and detail textures is documented only on forums, and those posts partly conflict ([assettocorsamods](https://assettocorsamods.net/goto/post?id=20528); [Cimmerian guide](https://cimmerian.gitbook.io/assetto-corsa-conversion/changing-the-car-look/making-the-car-look-good)). The diffuse alpha channel must therefore be passed through unchanged.

### One car-coordinate frame makes patterns and logos line up

Patterns should be generated once in a car frame, with x along the car from the front, y up from the sill and z across. Each island then gets a 2×3 affine map from car coordinates to texture pixels, registered by least squares on the arch centres for the sides and on the bounding-box ends for the top, front and rear. Sampling runs through the inverse affine, inside the filled mask only. Stripes should be rotated by each island's PCA tilt, or they will visibly climb along the car. One mirror rule matters. Geometric content maps through the pure flip, but readable text has to sit at the mirrored position **and be rotated 180°**. The hand-made `CRT-Kris` skin, which is used in game, shows exactly this: its "713" and its sponsor lettering on the lower side island are rotated 180° relative to the upper one ([CRT-Kris_rgb.png](file:///D:/ClaudeData/tmp/uvseg_test/CRT-Kris_rgb.png)). Logos are dragged on the 2D view, guided by a distance-to-edge map. On Talbot side islands, 84–89 % of pixels are at least 10 px from an edge and 50–59 % at least 40 px ([probe 2](file:///D:/ClaudeData/tmp/uvseg_test/uvseg_probe2.py)). The drag shows which island the logo is on, what share of it hangs outside, and whether it is near an edge. Thin dark ridges in an AO bake mark door shut lines to warn about. After compositing, padding pushes island colours outward so DXT blocks and mipmaps do not pull in background colour. The minimum is 4 px, because DXT works in 4×4 blocks, and about 8 px is the target at 2048². The usual guidance is gutters at least twice the padding ([Substance 3D Painter: dilation](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/technical-support/workflow-issues/export-issues/texture-dilation-or-padding)). The app's existing `pad_texture()` was written for exactly this seam problem ([skingen.py](file:///D:/Claude/Claude-/ac-skin-generator/skingen.py) lines 3152–3179).

| Pitfall | Symptom | Mitigation |
|---|---|---|
| Dark paint taken as background | shattered islands (`ratty_s`) | mask from AO, wireframe or union of skins |
| Stacked UVs (both sides on the same texels) | a big side island with no mirror partner; text reads backwards on one side | warn; offer "symmetric designs only" for that island |
| One panel split by seams | several islands for one panel | shift-click to group islands |
| AO baked for another slot or UV set | AO coverage differs from the skin's by more than 5 % | reject that source, use the next |
| DXT1 transparent-black mode | black specks at edges | pad first; avoid pure black next to transparent texels |
| CM-made AO quality | blocky squares, sometimes an all-black output ([Overtake thread](https://www.overtake.gg/threads/alternative-ways-to-generate-higher-resolution-ao-maps.157626/), snippet) | sanity-check histogram and coverage before use |

## The recommended 2D mode: a sealed path behind the protection detector

The non-negotiable rule from the app's own plan is that nothing may change for cars that work now ([TODO.md item 2](file:///D:/Claude/Claude-/ac-skin-generator/TODO.md)). The cleanest way to guarantee that is architectural. All 2D code lives in a new module, say `template2d.py`. It is reached from one branch: the point where the app already concludes "protected" and today falls back to a plain colour, either through `scrambled_uv` on the main paint texture or through the "protected (locked)" parse error. Shared functions are not edited. `label()` is added beside `enclosed()`, not in place of it, and the new placeholder-texture check only adds information, never changing the existing decision. With that structure, `tests/same_output_cars.py`, which fingerprints every preview, log line and written file for both design variants, should report IDENTICAL on every working car, and it becomes the gate for every phase. A 0-byte kn5 gets a "broken install" message rather than 2D mode.

The mode then gathers its inputs from plain files only, ranked by quality. The app chooses automatically, shows its choice, and lets the user switch.

| Rank | Source | Where it lives | What it supplies | Caveat |
|---|---|---|---|---|
| 1 | Maker template skin | `skins\Template*\` (PNG/DDS body, `Wireframe.png`, AO) | clean base, island mask, shading, `ext_config.ini` | layout varies by maker; PSD/XCF only listed for the user |
| 2 | AO map | `*_AO*.dds` in any skin | island mask and S | sometimes a working texture for another slot (coverage check) |
| 3 | Wireframe | `*wire*.png` | island outlines via `enclosed()` then `label()` | lines only, no shading |
| 4 | Union of all skins | every `skins\*\<paint texture>` | coverage | needs two or more skins |
| 5 | Lightest stock skin | its body texture | base and fallback S | old logos ghost through |
| — | `ui/cm_paintshop.json` + `ui/cm_paintshop/` | car `ui` folder | texture names, defaults, number positions, masks | kn5-only references give names but no pixels |
| — | kn5 material table (state a) | the plain part of the kn5 | which texture is the paint (e.g. `EXT_Carpaint_*` → `EXT_Skin_Colour.dds`) | state (b) cars must use skin and paintshop file names instead |

The flow has five stages, and the user decides at clearly bounded points. First, the app tells the user that the car is protected and that a 2D template was found in source X, and offers "Paint the 2D layout" next to the existing plain colour. Second, it builds the island map and shows it as a coloured overlay labelled Top, Left side, Right side, Front, Rear and Small parts. Two one-click questions are mandatory unless the per-car cache already holds the answers: "which end is the front?" and "which side is the left?". Grouping, splitting and marking "don't paint" islands (glass, lights, carbon, number plates) are optional. Third, it paints. Colours go through the shading ratio, with S taken from AO where available. Patterns are sampled through the per-island affines. Logos and numbers are dragged on the layout, starting from `cm_paintshop.json` positions where they exist, with green, amber or red edge feedback and optional auto-mirroring under the 180° rule. Any amber or red placement needs a confirmation, as with today's "pick it on the car", which becomes "pick it on the layout". Fourth, it writes a **new** skin folder:

- the paint texture under its exact name and source size;
- encoding DXT1 when the source alpha is fully opaque, otherwise DXT5 with the source alpha copied unchanged;
- padding applied before encoding;
- the source skin's `ext_config.ini` copied verbatim, so body-kit switches survive;
- `ui_skin.json` and `livery.png`;
- the design saved to `r4s_design.json` under a separate 2D key, so the skin reopens for editing without disturbing the 3D readers.

At 4096², DXT1 comes to about 8 MiB and DXT5 to about 16 MiB, against 89.5 MB for the 296's uncompressed sheet. That meets the "lighter files" goal. (Pillow 11.2.1 and later writes DXT1/DXT5 ([Pillow DDS docs](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html)), and an AC skinning guide recommends DXT5 at 4096 or less ([AC skin guide](https://sites.google.com/view/acskinguide), snippet).) Fifth, the app asks for an in-game check, because it cannot render the car. A "looked wrong" answer feeds the existing "Report this car" zip.

The limits should be stated in the UI, not discovered by users. There is no 3D preview: the in-app view is the flat sheet with AO multiplied and an optional wireframe overlay. `preview.jpg` cannot be a render. Previews of encrypted cars are a known community problem, and a photo-mode workaround exists ([OverTake download](https://www.overtake.gg/downloads/preview-as-a-photomode-location.59498/), snippet). Continuity from side to bonnet or bumper is approximate, because nothing in an image says where islands meet in 3D. Recognition has been proven on one unprotected layout only. Of the 153 cars, 53 lack templates and must lean on stock-skin textures, and cars with neither stay on plain colour. Stacked UVs cannot be detected from pixels, only suspected.

| Risk | Why it matters | Mitigation |
|---|---|---|
| Regression on working cars | the app's top rule | sealed module, single entry branch, no edits to shared functions, `same_output_cars.py` on both variants every phase |
| Crossing the protection line | policy and goodwill of makers | read only skin, `ui` and name tables; UVs read for detection only; never write the kn5 or `data.acd`; no GPU capture; say so in the README |
| Old livery ghosting through companion textures | per-skin textures such as the 296's 4096² `EXT_Skin_Map.dds` carry per-livery data (an untested hypothesis; iRacing shows the same effect when default paints carry spec maps ([Trading Paints](https://help.tradingpaints.com/painting/on-some-vehicles-logos-appear-faintly-ghosted-underneath-my-custom-paint-how-can-i-prevent-this/))) | take companion textures from the Template skin first; test in game in Phase 0 |
| Wrong diffuse alpha | the alpha drives the detail and reflection blend | copy the source alpha unchanged |
| Wrong orientation | text reads backwards, stripes run the wrong way | mandatory confirmation, cached per car |
| Unreadable DDS variants | the Pillow docs consulted do not list BC7 | detect it and ask for a PNG export of the template |

## Build it in six gated phases

The algorithms were tested on an unprotected car, so the plan starts with evidence, not code. Every later phase must pass `same_output_cars.py` before it ships, and the multi-sim work comes last because it reuses everything before it.

## Conclusion

The plan rests on one point: in Assetto Corsa, the protection boundary and the painter's interface coincide. The skin folder is both what the maker leaves open and what the game reads. A tool that stays on that side of the line needs no special permission and no clever workaround. It needs better image understanding than any existing livery tool attempts, plus one or two honest clicks from the user. That reverses the app's current hierarchy. The 2D engine is not a consolation prize for protected cars but the general engine, because every other sim paints only in 2D. The 3D texel path becomes the special case that unprotected AC cars happen to allow. The design decision that makes this pay off is keeping paint, shading and finish as separate layers from day one, since AC wants the shading baked in, rF2 forbids it, and each sim encodes finishes differently.

The open risks are empirical, not algorithmic. Nobody has yet checked whether a protected GT3's layout segments as cleanly as the Talbot's, whether the per-skin companion textures and the diffuse alpha behave in game as assumed, or whether CSP's in-game Paintshop can serve as the missing 3D check. Phase 0 answers all three in an afternoon of probes and one test skin per car. It should come before a line of the 2D mode is written.
