Setup Coach - changelog
=======================

Newest first. Moved out of SetupCoach.lua in v2.6.2 so the code carries no
version history; every change from here on is written here.

Setup Coach  3.1.0

3.1.0: LEVERS BACK, LESS STRICT; BALANCE TARGET; DAMPERS FROM A REAL
HISTOGRAM. Nik: "Nothing except camber and tyre pressures get written via
the optimal setup button. It should go back to the way it was before, but
with less strict levers. It would also be good to have an option to choose
between a normal, oversteer and understeer setup. Damper and suspension
settings need revisiting... research, investigate, fix it."

Why 3.0.0 wrote so little: balance (ARB, toe, wings, diff, rake) became
advice only, and the damping-ratio bands (bump 0.30-1.20, rebound
0.50-1.50) were wide enough that no damper ever sat outside them. The
27 v3.0.0 Builds wrote springs, pressures, camber and the odd packer.

1. Back to the 2.6.2 code: lever chains, bottoming chains, floor
   clearance, collider floor, branch passes.
2. Less strict levers. A lever gets three tries before it freezes (was
   two); a 10% drop counts as helped (was 15%); moves that showed no
   effect are KEPT, not put back (a one-click effect is usually inside the
   lap-to-lap noise, so "no effect" mostly meant "not measurable yet"); a
   pass with no measurable gain starts the next pass instead of stopping
   the branch; 4 passes (was 3). Lever history from the strict rules is
   cleared once on load. The put-back machinery stays in the code, off.
3. Balance target - Normal / Oversteer / Understeer buttons above BUILD
   and in Settings (settings.balanceMode):
     Normal      tight if push > 1.15x snap (was 1.25), loose if snap >
                 1.15x push and > 25 snaps per 100 corners; bias +1%
     Oversteer   tight if push > 0.85x snap, loose only if snap > 1.6x push
                 and > 40 per 100; bias +0%
     Understeer  tight only if push > 1.6x snap, loose if snap > 0.85x push
                 and > 8 per 100; bias +2% (more forward = more stable)
   Brake bias still writes once per car; re-arm it in Settings after
   changing the target if you want the new margin.
4. DAMPERS - what was wrong. The slow-damper decision came from "events":
   frames where wheel velocity passed 0.54 m/s. (a) 0.54 m/s is ten times
   the car's slow/fast knee (DAMP_FAST_*THRESHOLD, 0.03-0.14 m/s on Kunos
   cars; race-engineering low-speed band 25-75 mm/s), so the SLOW settings
   were tuned from kerb-strike speeds the FAST settings control. (b) The
   two sides were counted differently: bump at most once per 0.8 s and not
   during kerb cooldowns, rebound every frame (front only while steering
   past 12 deg). So the counts leaned to rebound and depended on frame
   rate - the "structural bias" that got the rear histogram retired in
   1.9.8 was this, not the car.
   Now: every frame, each wheel's velocity adds dt seconds to a bin - bump
   or rebound, slow or fast at the car's own knee (0.02-0.15 m/s, else
   0.05), ignoring under 5 mm/s and glitches over 3 m/s. Banked per lap.
   Verdict per end: bump share of the moving time. Over a lap the wheel
   goes up as far as it comes down, so the side with less of the time is
   moving faster - the under-damped side (the damper-histogram rule:
   bump and rebound halves should be about symmetric). Under 44% -> bump
   soft for its rebound; over 56% -> rebound soft; needs 20 s and the same
   lap-consistency rule as every verdict. One click a Build on the slow
   setting: stiffen the soft side unless it is at its limit or its damping
   ratio is at the ceiling (bump 1.25, rebound 1.80), else soften the other
   side (the 0.30 / 0.50 floors still apply). Both ends now - the rear too
   when the balance chain has no rear verdict. An end running out of
   travel still belongs to its bottoming chain. Panel lines say the same.
   Log: "damper histogram F: bump x% / rebound y% of the moving time ..."
   in the Front/Rear dampers lines.

Sources (D:/Claude/research_notes/AC springs and dampers setup/): Kaz
Technologies damper guide, OptimumG Springs & Dampers tech tips, HP
Academy histogram lesson, Kunos suspensions.ini comments, CSP Lua SDK.

Tests: test_v310_relaxed_levers.lua (19), test_v310_damper_histogram.lua

Setup Coach  3.0.0

3.0.0: THE CALCULATED BASELINE. Nik: "Make a plan and then get started.
i like your ideas and that sounds like a logical way of doing it. Clean
up the .lua so it isnt full of notes from previous versions and fixes."
Plan: docs/plans/2026-10-20-calculated-baseline.md.

1) WHY. A Build that searches for the optimum by moving one lever,
   judging it next window and branching needs far more clean laps than a
   driver gives between presses, and lap-to-lap noise is bigger than a
   one-click effect - so the chains' HELPED / NO EFFECT verdicts were not
   reliable, and balance is the driver's call anyway. Much of a setup
   does have a physics answer from the car's own files, checked by the
   telemetry. That part is now calculated; the rest is coached.
2) BUILD = ORDERED CALCULATORS, each with its own log line:
   - SPRINGS: sprung natural frequency sqrt(k/m)/2pi kept inside a band
     for the car's MEASURED downforce class (wheel loads on straights,
     load = W + k v^2, ratio at 200 km/h: low < 15 % -> 1.5-2.5 Hz,
     medium < 70 % -> 2.0-3.5 Hz, high -> 3.0-5.0 Hz, 1.5-3.5 Hz until
     measured). Stiffer when the median lap uses over 95 % of the travel
     (never past the band top for travel alone), softer only above the
     band with travel to spare (< 80 % used). Max 10 % a Build.
   - SLOW DAMPERS: damping ratio c / 2 sqrt(k m) with the new springs.
     Bump 0.30-1.20, rebound 0.50-1.50; a setting outside its band moves
     just inside it in one move, inside it is left alone. Vanilla DAMP_*
     only.
   - RIDE HEIGHT TO THE FLOOR: as 2.6.0/2.6.2 (10 mm off the collider
     floor, never into the aero stall).
   - BOTTOMING: an end running out of travel on most clean laps gets one
     fix a Build after the springs: packers > fast bump > ride height +1.
     The slow-bump and springs links of the old chain are gone (springs
     have their own calculator; slow bump has its ratio band).
   - BRAKE BIAS: the one-time calculated write, unchanged.
   - PRESSURES and CAMBER: unchanged.
3) BALANCE IS ADVICE ONLY. Anti-roll bars, toe, wings, diff and rake are
   never written. The panel lines give the options ("... - Build leaves
   balance to you"); the ARB / toe / diff / aero module toggles are gone.
4) REMOVED: lever chains, branch passes and put-backs, the per-car lever
   ledger and pending-move judging (settings leverLedger, leverPending,
   branchState - old values are simply ignored), the effect lines, the
   front-damper histogram writer, the rear rebound experiment, the
   "Reset lever history" button, NUDGE_FRACTION and the ABS writer stub.
5) PANEL: SPRINGS shows the frequency band and downforce class; slow
   dampers show the damping-ratio bands; FLOOR line as 2.6.2.
6) LOG: new lines "springs:", "dampers (damping ratio):", "floor:",
   "bottoming:". Version tags dropped from log labels ("collider floor:",
   "calculated targets:", "held slides:", "evidence units:", "track
   contacts (logged only):").
7) CODE HYGIENE. Every version note, bug story and "used to / until now"
   narrative is out of SetupCoach.lua (the file is about 800 lines
   shorter); comments say what the code does and why.
   History lives here only. CLAUDE.md rewritten for v3 (the old one is
   docs/archive/CLAUDE-v2.6.2.md).
8) TESTS. Lever-chain and branch-pass tests removed;
   test_v300_calculators.lua added (springs band / travel, damper ratio
   bands, no balance writes); floor tests renamed
   test_floor_clearance.lua. About 900 checks, all passing.

Setup Coach  2.6.2

2.6.2: THE COLLIDER IS THE BOTTOM OF THE CAR. Nik: "add something that
tells if the car is hitting the floor. it should look at the collider
and treat that as the bottom of the car."

1) WHY. The floor was car.rideHeight - two pickup points (car.ini
   [RIDE], from the CG) - and those are not where the body touches the
   track. From the extracted cars: the Abarth's collider floor is 20 mm
   BELOW its pickups (scrapes while ride height reads 20 mm), the
   Sunbeam's 40 mm above them, the Huracan's level with them.
2) HOW. The ground colliders (colliders.ini CENTRE / SIZE from the CG,
   GROUND_ENABLE, the [HEADER] COLLIDERS count; CSP's
   ac.getCarColliders when the file has none). Every frame on track the
   four bottom corners and the bottom centre of each ground box go into
   the world with car.transform and a ray is cast straight down
   (physics.raycastTrack). The lowest point per end - front ahead of
   the CG - feeds the floor histograms (so the Build's floor step) and
   the floor-hit counts. A pitch of 1 deg nose down brings the
   Huracan's front corner 40 mm closer than the pickups say.
3) CHECKED LIVE, NOT ASSUMED. The same rays are cast from the two
   pickups (axle lines from suspensions.ini) and compared with the
   car's own ride height: within 25 mm over 300 frames per end the
   collider is used ("verified"); outside it, or if the transform's
   axes don't match car.look/up, the pickups stay in use and the log
   says why with both numbers. A car without pickups or reporting no
   ride height is used "unverified".
4) WHERE YOU SEE IT. A FLOOR line in the panel (hits per end this
   window, the closest the floor came, what measured it), and a
   "collider floor (v2.6.2)" line in every Build log.

2.6.1: NO KERB SOFTENING, AND REBOUND FOLLOWS THE SPRINGS. Nik: the
kerb softening block "it's useless. abolish it." / "at some point, maybe
the 3rd or 4th press of the build button, the car becomes really
bouncy. the next build doesn't rectify this".

1) THE FAST-DAMPER KERB SOFTENER IS GONE. It softened fast bump and
   fast rebound whenever fast events crossed threshold (kerbs, not a
   verdict on the dampers), floored at the factory default since
   v1.9.4. Fast dampers now move only through the bottoming chain's
   fastBump lever. The panel no longer advises softening them either.
2) WHY IT GOT BOUNCY. A damper's ratio is c / 2 sqrt(k m). The v2.6.0
   bottoming chain stiffens springs (+10% a Build) and bump but never
   rebound, so each spring move left the same rebound damping that
   corner less: in the truck log at Hockenheim (Builds #151-#153) the
   rear springs went 200 -> 250 and the front 200 -> 225, and front
   rebound fell 0.44 -> 0.41 with the front spring move alone (0.44 /
   sqrt(1.125) = 0.415) - just over the old 0.40 floor, so nothing put
   it back. And the floor pre-pass runs BEFORE the chains, so it
   checked the ratio against the springs the Build was about to change.
3) REBOUND FOLLOWS THE SPRINGS. Each corner's slow rebound (value and
   ratio) is snapshotted before the chains run; after them, a corner
   whose ratio fell while its rebound was left alone has its rebound
   raised in the same Build, back to where it was and never under the
   floor. Logged as "rebound follows the springs".
4) REBOUND FLOOR 0.40 -> 0.50. Overshoot after a bump is
   exp(-pi z / sqrt(1 - z^2)): about 25% at 0.40, 16% at 0.50. The floor
   pre-pass lifts any corner under it on the next Build - that is what
   makes the Build after a bouncy one put it right - and the same floor
   stops any lever softening rebound below it.

2.6.0: BOTTOMING ONE FIX AT A TIME, RIDE HEIGHT TO THE FLOOR. Nik:
"Bottoming - one at a time. Ride height least important. Stiffening
springs too much loses grip so be cautious." / "App shouldn't just lower
a car to aero peak - it should lower until the car is at minimum
available without the body of the car striking the floor."

1) BOTTOMING, ONE FIX AT A TIME. Until now every Build that saw
   bottoming changed springs, slow AND fast dampers (bump and rebound),
   packers and ride height together - on the Sunbeam the dampers climbed
   2 clicks a Build and no window could say which change did anything.
   Now each end that runs out of travel on most clean laps has its own
   chain, worked like the balance chains: ONE move per end per Build,
   judged by the next window, frozen after two moves that did nothing,
   put back at the end of a pass that made no difference. The order:
     packers      more travel before the packers
     slow bump    stiffer, more support through the stroke
     fast bump    stiffer, the hit that reaches the end of the travel
     springs      the calculated rate, at most +10% a Build (was 30%),
                  aiming at 95% travel use on the median lap (was 92%)
     ride height  up one click - last, it costs grip and aero
   A car without an item skips it and says why (the Sunbeam v6 has no
   adjustable packers or dampers: springs, then ride height). The chains
   run before the balance chains - the platform first.
2) BUMP, NEVER REBOUND. Bottoming used to stiffen rebound too, on the
   idea that too-soft rebound lets a car creep down onto its stops. It
   is the other way round: too MUCH rebound packs a car down over a run
   of bumps - the wheel isn't back before the next one compresses it
   again. Rebound is no longer touched for bottoming, slow or fast.
3) RIDE HEIGHT TO THE FLOOR, NOT TO THE AERO PEAK. The front used to be
   moved toward the height where its downforce peaks however far that
   was from the floor (the Huracan GT3 Evo2: "lower to 22 mm" on a car
   running 62). Now the app measures how close the floor gets to the
   track on every clean lap (at the car's own ride-height points,
   ignoring the lowest 0.5% of the lap - a kerb strike) and brings the
   lowest end to 10 mm off it: raised at once when it is closer,
   lowered when there's room - never into the aero stall (the splitter
   and diffuser kept above the height where their downforce falls
   away), never while an end runs out of travel or uses 90% of it, and
   only with a reliable pit calibration at both ends. Both ends move by
   the same millimetres, so the rake the balance levers chose is kept;
   3 clicks a Build at most. A Build that moves ride height here holds
   rake and the bottoming ride raise; a raise holds the bottoming chains
   too (one change at a time).
4) NEW IN THE LOG: "floor (v2.6.0)" (clearance per end, floor contacts
   per lap, stall room, calibration, what it did) and "track contacts
   (v2.6.0, logged only)" - body contacts with the track and where on
   the car, collected to check before anything uses them. Bottoming
   moves read "Bottoming front/rear: lever ... moved"; their branches
   and ledger are in the branches / levers lines like the balance ones.
   The panel says the same: SUSPENSION names the chain, SPRINGS says
   springs come 4th, and dampers on an end that runs out of travel are
   "left to the bottoming chain".

Verified in test_v260_bottoming_floor.lua and test_branch_passes.lua
(the chain runner driven Build by Build). Not tested in game yet.


2.5.2: FIVE BUGS FROM THE FIRST WEEK ON v2.5.1. 57 Builds, 29 Sep - 4
Oct: the Sunbeam (live, the v6 backup and the +10% copy) at the
Nurburgring GP, Bathurst, Brands Hatch, Knockhill, Blackwood and a
gravel stage; the Huracan GT3 Evo2 and the Audi R8 LMS Evo II at Imola.
The physics fingerprint caught both Sunbeam physics changes and reset
what it had learned; held slides, range limits and summaries worked.
These didn't:

1) RESET TELEMETRY LOST THE CAR'S TRAVEL RANGE. reset() put the travel
   limit back to the made-up 0.12 m ("not read yet") and refreshTargets
   never re-read it for the same car - only a pit stop did. 16 Builds
   judged bottoming and sized springs against 120 mm (Sunbeam front 140,
   Huracan Evo2 64, Audi 75). The gear-ratio reads were lost the same
   way. Now a reset marks the car data stale and the next frame re-reads.
2) DAMPERS STIFFENED "FOR BOTTOMING" ON INCONSISTENT HITS. The slow-
   damper bottoming move read the raw max-travel count (3 hits in the
   window), not the lap-consistency test the spring writer uses - one
   Build said "max-travel hits seen in only 3 of 7 laps - left alone"
   and stiffened all four rear damper settings for the same hits. Most
   of the Sunbeam's +2-clicks-a-Build damper climb. Now through
   travelHitsConsistent, like every other writer (v2.0.0 rule).
3) BRAKE BIAS. A wheel in the air under braking (gravel crests) had no
   grip-model force, so those samples counted for the load split but not
   the grip sums; on 4 Oct the grip count fell under 30, the target fell
   back to load alone, and the Sunbeam v6's one-time write went out on
   it (5 zones, lap gate overridden). Now: such samples aren't braking-
   balance samples; a car whose tyres have a grip model never falls back
   to load; and the one-time decision waits for a Build that passed the
   lap gate (30 Sep it was HELD on 11 corners).
4) RIDE-HEIGHT DIRECTION FROM NOISE. "Direction measured in the pits"
   was the sign of one pair at >= 0.05 mm/click, across spring changes
   that move static height by themselves: the Sunbeam's front went +0.60
   -> -0.09 -> +0.46 mm/click in ten minutes and "raise" went 27->29->
   27->29 while it was bottoming. Now pairs need the same spring setting,
   and a direction needs 2+ pairs agreeing on the sign with a median of
   0.3 mm/click or more; the aero ride-height target needs the same (the
   Evo2 was lowered toward its peak on 1.00 mm/click from 1 pair).
5) PRESSURE IGNORED THE LIVE SETUP WITHOUT A TEMPLATE. The base was
   "template only" (older than the live sync): Evo2, no setup file, live
   18 psi, hot 23.5 vs 26 -> wrote 28.5 cold; next window 33-37 hot.
   Now the value on the car, template or live: 20.5.

Also: "first time this car is seen" holds until a Build reports it and
isn't repeated after; the diff says "to back up the preload increase"
only when the preload went up.

Verified in test_v252_log_review_fixes.lua - each fix reverted on its own
turns its checks red.


2.5.1: BUILD WAS PUTTING THE GEARS IN THE WRONG SLOTS. Reported on the
Huracan GT3 at Silverstone: "build button messed up the gears. it's not
even supposed to touch them." No writer touched them - v2.1.1's CARRY
did. It copies every unmanaged live value into the output so loading the
file leaves the driver's choices alone, and it matched them by name.

CONFIRMED FROM THE FILES. CSP's ac.getSetupSpinners() names the gear
spinners INTERNAL_GEAR_1..6 (forward gear n, the car's setup.ini
[GEAR_n]); AC's own saved setups name the same items INTERNAL_GEAR_2..7
(AC's gear index: 0 reverse, 1 neutral). None of the 1500+ saved setups
on this PC has an INTERNAL_GEAR_1 - v1.8.0's "invented" one was CSP's
1st gear. So each gear's value went into the gear below it. The
18:35:15 Build wrote 5th = 0.8857, the same ratio as 6th, where the
car's physics had 5th at 1.0312; 1st (2.1579), 3rd (1.5217) and 4th
(1.3076) were shifted too, and 1st's own value was dropped. Put back one
slot up, the live values are the car's stock 2nd-6th with the driver's
4.1666 final drive - one consistent car - and the log's own counts only
add up that way (10 carried, 2 left out: INTERNAL_GEAR_1 had no section,
INTERNAL_GEAR_7 had no spinner). It never showed before because this was
the first Build since v2.1.1 on a car whose gears are adjustable one by
one - the others carry only the final drive, TC or brake power.

FIX: alignLiveGearNames renames the gear spinners before the live sync.
The offset is read from the two name sets, never assumed - the template
is AC's own file: live + 1 == template -> renamed; equal -> CSP already
matches (a future fix), left as is; anything else -> gears are not

WRITES gearing; it now carries it into the right slots.

Log: the liveSetup line gains "gears renamed: CSP INTERNAL_GEAR_1..6 =

exact gearbox that file got.


2.5.0: WHAT THE v2.4.0 LOGS AND THE SUNBEAM PROJECT SHOWED. 21 Builds on
four cars (Escort Mk2, Dacia, Camotos R6, and Nik's own Talbot Sunbeam
Lotus mod - a live rear axle, no bars, no adjustable dampers, physics
changing under one car id). The driver: "build all"; the Sunbeam is a
work in progress and may gain dampers etc. later, so nothing below is
specific to it - it all follows what a car HAS, and notices when that
changes.

1) TRAVEL RANGE = THE CAR'S OWN PACKER_RANGE. readTravel read a TRAVEL
   key no car has (ten checked) and measured every car against a made-up
   0.12 m: GT cars (Huracan packers 55 mm) could never register
   bottoming, long-travel cars (the Sunbeam, 140 mm) registered it early
   and got ride height raised and springs stiffened every Build. Now
   suspensions.ini PACKER_RANGE per axle, the live setup's adjustable
   packers per corner (mm on every car checked), every corner against
   its own range; static travel captured at rest in the pits (the
   Sunbeam sits at 45%). The panel and the log show share of the car's
   range.
2) LONG TRACKS COUNT IN SECTIONS. The lap gate was overridden on 18 of 21
   Builds; the Nordschleife never banked a lap, so noise, measured
   jumps, group verdicts and the spring target never ran there. A lap
   over 7.5 km is split by spline position into ~5 km sections (Nord: 4)
   and each is a unit of evidence, exactly like a lap. Ordinary tracks
   are unchanged. The unit in progress when a Build consumes the window
   is partial (it started before the Build, on the old setup).
3) BRAKE BIAS FROM GRIP, NOT LOAD. The target used the front's share of
   the LOAD (Sunbeam: 76%, target 77%) - but AC tyres grip less per kilo
   as load rises, and at 69% the fronts already locked first. The tyre's
   own model (DX_REF / FZ0 / LS_EXPX, or DX0/DX1) now gives the front's
   share of the GRIP (69.0% -> target 70.0%). Handbrake use is kept out
   of the braking samples and the rear-lockup count; the BRAKE line says
   when the lockups disagree with the calculation (they outrank it).
4) CARS WITHOUT BARS OR DAMPERS GET REAL LEVERS. On the Sunbeam only
   front toe was left in the chain. SPRINGS (the roll-stiffness split -
   rear softer / front stiffer for oversteer, the reverse for push) and
   DIFF COAST (lift-off/entry only; the diff writer never touches coast)
   join the low-speed chains after the ARB and dampers. The rear-damper
   lever says "no adjustable rear dampers on this car" instead of
   "already at their softest"; the ~20 SKIPPED lines a Build printed for
   parts the car doesn't have are one summary line.
5) PER CAR + TRACK RECORDS. The last-Build record and the pending lever
   moves held one car: a Camotos Build wiped the Sunbeam's, and a
   Sunbeam Build at Adelaide was checked against its Nordschleife setup
   (NO -> moves never judged). Both are kept per car + track now; the
   old single records are still read.
6) HELD SLIDES. Every car logged 50-140 "snaps" per 100 corners. A slide
   started with the handbrake, or held on the throttle for over a
   second, is deliberate: its counts move to heldSlides (logged, never a
   verdict). Real snaps count exactly as before, so the 25-per-100
   calibration stands.
7) PHYSICS FINGERPRINT. The Sunbeam went v1 -> v3 in a day under one id
   and the app kept what it had learned. Every physics file is hashed
   (parsed content, via ac.INIConfig sections) plus the final-drive
   list; on a change, the brake-bias one-time write is re-armed and the
   ride-height calibration, camber gain, lever history, branch passes,
   pending moves and last-Build record for that car start again. The
   next Build and the panel say so.
8) RANGE LIMITS NAMED. When the car's setup range - not the calculation -
   stops a target (the Sunbeam wanted -5.3 deg camber against a -2.5
   limit), the change line and one summary line say so: the fix is to
   widen the car's range. Ride height follows the direction the pit
   calibration measured (no "verify direction" once measured).

Log: "held slides (v2.5.0)", "evidence units (v2.5.0) ... physics
fingerprint", travel as share of the car's range, the physics-change
and summary lines. Verified in test_v250_evidence_and_physics.lua.


2.4.0: BRANCH PASSES - THE CHAIN CYCLES BACK AND IS JUDGED AS A GROUP.
The driver: once a branch (ARB -> dampers -> toe ...) has been worked
through, go back to its start and monitor the group as a whole - and
put moves that did nothing back to their starting value. Until now a
lever frozen after two no-effect moves stayed frozen for good, each move
was judged only against the window just before it, and nothing knew
where the problem stood when the branch started.

1) A BRANCH = one signal (e.g. low-speed oversteer) on one car at one
   track. When it first acts, the problem rate, its lap-to-lap noise and
   the Build are recorded as the pass BASELINE; every lever move records
   the sections it changed (before -> after).
2) A PASS ENDS when the problem is gone, or when no lever in the branch
   can move (all frozen / at limits). The whole group is then judged:
   baseline -> now, against the same noise test as the per-click values.
3) PUT-BACK: every section a no-effect move changed goes back to the
   value it had before - the value after the last move that HELPED, or
   the pass's starting value. Moves that were never judged are kept.
   Skipped (and logged) if the section has changed since (driver or
   another module), its module is now off, or a guard refuses (damping
   floor, LUT curve, calculated target). Put-backs are a change like any
   other: the branch holds for that Build and the next window checks
   them - if the problem got worse beyond the noise (or came back), the
   put-back sections are RESTORED.
4) THEN: problem gone -> branch DONE (watching; if it returns, a new pass
   starts from the top). Improved beyond the noise -> next pass from the
   top, every frozen lever gets one more try (frozen now means "for this
   pass"), measured per-click values kept. No gain over a whole pass, or
   3 passes -> STOPPED, advice only; Settings resets it.
5) Also fixed: the ledger held ONE car - a Build on a second car wiped
   the first car's history. Now per car (last 30 kept; old records
   migrate). Pending moves now carry the track: a window on another
   track no longer judges them.

Log: "branches:" line (state, pass, baseline -> now, every move with its

2.3.0: CALCULATED TARGETS INSTEAD OF CLICK-STEPPING, WHERE ONE EXISTS.
The driver asked whether Build calculates an optimum or steps 1-2 clicks
by trial and error, and to jump straight to a calculated value wherever
one genuinely exists - advice staying as it was. Researched module by
module against the Huracan's own files and the logs, then built:

1) BRAKE BIAS - one calculated write per car, then ADVICE ONLY. Target =
   the split where both axles reach the limit together: the front's
   measured share of tyre load under hard straight-line braking (new
   accumulator, 4+ zones), corrected for tyre radii, +1% stability
   margin. The driver's condition: bias moves entry balance (forward =
   steadier, more push; rearward = more rotation, looser), so the write
   is capped at 3% and HELD if it would feed an entry problem the car
   already shows consistently. After it (written, already there, or
   held) Build never touches bias on that car; the BRAKE advice line
   carries the target, the lockup trims and the entry trade-off. The
   v1.x lockup +-1 writer is retired. Settings can re-arm it per car.

2) FINAL DRIVE - advice names the exact option: the ratio that puts rpm
   at the session's top speed at 97.5% of the limiter, matched to this
   car's final.rto (read in-game), with the fitted ratio from physics.
   On the limiter at Vmax it names the next longer option. Build still
   never changes gearing.

3) SPRINGS FOR BOTTOMING - calculated: travel scales with 1/k, so the
   rate that brings the MEDIAN lap's peak travel use to 92% is
   k x use / 0.92 (per-lap peak use is new in the lap bins; one kerb
   can't size a spring). Capped +30% per Build, rounded up on the grid.

4) FRONT RIDE HEIGHT TO THE AERO PEAK - the car's own ground-effect
   curve (Huracan front: 50 mm) vs the front's measured ride height in
   fast corners, moved in one go using a mm-per-click calibration the
   app learns from pit stops on different settings (fuel-matched pairs,
   median slope). Targets 2 mm above the peak (the stall side is below);
   capped at 3 clicks; the rake lever stands aside that window.

5) DAMPING-RATIO FLOOR - zeta = c / 2 sqrt(k m) from wheel rates and
   sprung corner mass. Physics gives a window, not a point, so this only
   lifts badly under-damped vanilla dampers (bump < 0.30, rebound < 0.40)
   to just above the floor in one move, and no lever may soften below
   it (the Huracan's setup allows rear rebound down to 0.18).

6) CAMBER - the "overshoots ~1.4x" item didn't survive the logs (gain
   0.48 / 0.78 / 1.6 across three Corvette Builds = scatter). Now: a
   noise dead-band of twice the loaded average's standard error, and a
   per-car measured gain once 3+ Builds span 0.3 deg. The "camber write:
   SKIPPED - sit in the pits" status line, wrong since v1.5.0, fixed.

7) BALANCE LEVERS - no first-principles optimum (the Huracan's roll-
   stiffness split says "understeer"; every log says loose), so they're
   solved from measurement: when the next window shows a lever's effect
   clearly above the lap-to-lap noise (2x the combined standard error of
   the per-lap rates), its per-click effect is stored and the chain then
   jumps it the clicks needed to reach the verdict boundary (cap 4; LUT
   bars 2; toe and rake always step). An effect inside the noise clears
   the estimate - no jump is ever sized from noise.

1.9.9: FIRST CORVETTE Z06 GT3 LOGS (four Builds in 17 minutes at the

reference" meant on the MECHANICAL GRIP line, and to check the debug.

1.9.8: SLIGHT OVERSTEER IS NOT A FAULT. The driver's rule, after the
drift-car discussion: "slight oversteer in a normal race car isn't a bad
thing, that should be noted". Noted, and built in: a car that rotates a
little is faster and nicer to drive than one that pushes, and the app
must not tune that out.

What was wrong. Every push-vs-snap decision judged the two signals
INDEPENDENTLY, or by "larger raw count wins":
  - ARB softened the front for any push count over threshold, AND the
    rear for any snap count - in the same Build - unless both aimed at
    the same bar. Both bars down = balance unchanged, more roll.
  - Rake did the same per end: a real Dacia log has "LF 5->4 (more rake
    for push)" and "LR 5->4 (less rake for oversteer)" in one Build.
    Both ends down, rake unchanged, the car just sits 1 click lower.
  - The advice panel's ARB line said "soften front" whenever push > th,
    even with more oversteer events sitting right next to it.
  - A slightly loose car was "corrected" toward push by all of them.

What's new. ONE verdict function, balanceVerdict, used by ARB, rake
(both regimes), wings, the rear damper signal, and every advice line
that promises what Build will do:
    tight  push > th and push > 1.25 x snap
    loose  snap > th and snap > 1.25 x push AND, at low speed, more
           than SLIGHT_OVERSTEER_PER_100 (25) snap events per 100
           corners - below that rate it's the rotation a race car
           should have, whatever the ratio says
    nil    left alone, with the reason logged: 'slight' (oversteer
           present, under the bar) or 'mixed' (both, neither dominant)
Understeer gets no rate floor on purpose - it's slow at any rate, and
the driver's point was about oversteer. High speed gets no rate floor
either: high-speed corners are a fraction of all corners, and a loose
car at speed is a real problem sooner.

Consequence for the rear dampers: a nil verdict now means LEFT ALONE.
The histogram fallback is gone from the rear - it is structurally
biased there (rebound events out-number bump in every real session), so
it resolved to "stiffen rear rebound" on exactly the slightly-loose cars
this version is meant to protect. The front keeps its histogram.

Real sessions under the new rule: the Dacia (push 76 / snap 65, 62
corners) is 'mixed' - ARB and rake are left alone instead of being
pulled toward push and then back; kinkl's Ferrari (rear signal 373 snap
/ 235 push, 81 per 100 corners) is still 'loose' - v1.9.3's fix stands.
New debug line "balance verdicts: low=... high=... rear=..." with the
snap rate, so the 25-per-100 bar can be tuned from real logs.

Verified in test_balance_verdict.lua; test_rear_rebound_direction.lua
updated for the rear's left-alone behaviour.


1.9.7: THREE THINGS FOUND WHILE LOOKING FOR A DRIFT-CAR LOG THAT WASN'T
THERE. The driver drove the BMW E30 drift car online for a few hours on
2026-09-18 and asked for the debug to be checked. There was no Build
entry from that day: the car's SetupCoach_Optimized.ini carried an
18th-of-September timestamp but was byte-identical to the 16th's Build
(Content Manager re-saves the selected setup on launch), CSP's own log
showed the app loaded clean, and the debug log's write path fails
silently. Conclusion: Build wasn't pressed. Along the way:

1) NUDGE SIZE IGNORED THE STEP. writeTuned sized every nudge as a
   PERCENTAGE OF THE CURRENT VALUE (frac x clicks x |cur|) - the only
   option back when no car had a readable schema - and used the schema
   only to clamp. On a control stored as a small click index that
   floors to 1 click and looks fine. On one stored as a big number it
   is absurd: the Ferrari's fast rebound is 175..190, and 8% of 185 is
   15 clicks - the entire range in one press. That is the actual
   mechanism behind v1.9.4's "185 -> 175 in ONE Build"; the direction
   ratchet chose the way, this chose the distance. A Dacia ARB sits at
   21079 on a 1000 N/m grid for the same reason. Now: when the step is
   known (spinner or setup.ini - since v1.9.6 that is every car), a
   nudge is `clicks` steps of that control, snapped to its grid; the
   percentage path survives only for a section with no step. Log lines
   say ", 2 clicks of 1000" so the size is visible.

1.9.5: THE LIVE DCAMBER READ NEVER WORKED - ON ANY CAR. The driver asked
why the Dacia Sandero Cup's camber was being judged by tread-temperature
spread instead of the tyre's own peak-grip angle. The Dacia has a
plain-text data/tyres.ini on disk with DCAMBER_0=1.3 / DCAMBER_1=-15
(peak -2.48 deg), it isn't in DCAMBER_LOOKUP, and the log said
peakCamberF=n/a. So the "CSP whitelists tyres.ini fields on encrypted
cars" explanation, held since 4.6.0, could not be right: nothing about
that car is encrypted.

The real cause is one argument. ac.INIConfig:get(section, key, default)
uses the DEFAULT'S TYPE as its return type - the SDK says so: "defines
type of value to return ... If not set, list of strings is returned."
Every read that passed nil (DCAMBER_0/1, DY0, PRESSURE_STATIC) got a
string list back even when the key was present, and tonumber(list) is
nil. PRESSURE_IDEAL was read with a numeric default, so it worked -
which is exactly the "pressure reads fine, DCAMBER doesn't" evidence
the whitelist theory was built on. The log confirms it: every peak
angle ever recorded (2.42, 3.09, 3.38) is a DCAMBER_LOOKUP value; the
two cars not in the table (Dacia, F2004) show n/a; no live read ever
succeeded.

one that computes a real target from this tyre's own coefficients and
goes to it in one press - now runs on every car whose tyres.ini carries
the coefficients, not just the 102 hard-coded ones. On the Dacia session
that prompted this: loaded front ran -1.45 deg against a -2.48 deg peak;
the thermal proxy's 0-12 degC dead zone called that "in the window",
the DCAMBER route will call it a degree short. (2) DY0 now reads, so
MECHANICAL GRIP can show "% of this tyre's peak" instead of raw dy.
(3) PRESSURE_STATIC reads (stored, unused since the delta method).
The lookup table stays as fallback and the live value takes priority.
New debug fields: peakCamberSrc=live|lookup|live+lookup|none, dy0=F/R.

Same bug, deliberately NOT switched on yet (each is its own decision):
setup.ini MIN/MAX/STEP in readSetupItem - going live would out-rank the
baked schema and re-introduce the v1.7.1 camber-units bug, and v1.8.0's
live spinners already give real ranges with the game's own multiplier;
aero.ini wing/LUT names - would start exercising ac.DataLUT11 in app

Verified in test_ini_default_type.lua against the Dacia's real

1.9.4: PRE-RELEASE PHYSICS AUDIT. The driver asked, before a new test
build, for every module to be checked against what the car is actually
doing on track - the lesson from rear rebound generalised. The signals
themselves came through clean: push/snap is textbook slip-angle
differential, lockups/wheelspin/diff signals all come from slip ratios
that genuinely measure the phenomenon. What did NOT come through clean
were three more LEVERS THAT COULD ONLY TURN ONE WAY - the exact defect
behind rear rebound - plus a mislabel and a misnomer. All fixed.

1) WINGS were a one-way ratchet. Direction hard-coded +1 for both;
   front rose on every high-speed push, rear on every high-speed snap,
   BOTH fired in the same Build when both crossed threshold, and nothing
   could ever bring either down. A mixed car at high speed walked both
   wings to maximum and paid in drag on every straight with no signal
   that would push back. Real log: front splitter pinned at max, rear
   wing 5->6->7. Aero balance is a RATIO, like ARB: high-speed push is
   cured by more front OR less rear, and less rear costs less drag. Now
   mirrors the ARB writer exactly - prefer adding to the axle that wants
   more, but if that wing is near its maximum reduce the OTHER one; when
   both signals fire, act only on the larger and name the other; near-
   max snapshotted once before either writes (the v1.4.1 self-
   cancellation lesson).

2) FAST DAMPERS were a one-way ratchet on any bumpy track. Without
   bottoming the direction was always softer - but fast events measure
   "this track has kerbs", not "these dampers are too stiff", so they
   walked to the schema minimum Build after Build. Real logs: fast
   rebound 185->175 (the Ferrari's floor, ONE press), 21->18->17->16 over
   three Builds on the Lotus, fast bump 81->68->66. AC's own tooltip:
   too-low fast rebound "can provoke a bouncing of the tyres ... making
   the front end lose grip on bumps and kerbs". The soften direction is
   now floored at the control's FACTORY DEFAULT (defaultValue from the
   live spinner API) - a reasonable first move stays reasonable, but the
   app no longer pushes past the manufacturer's own setting with no
   evidence it's helping. Stiffening (bottoming) is untouched. The
   driver noted fast rebound rarely fires - correct (6 writes vs 70 for
   fast bump in one log) - but when it does, the Ferrari case shows it
   going straight to the floor in a single press.

3) LABEL: low-speed oversteer lowers the REAR (correct - less rake
   counters oversteer) but the log line said "more rake". Copy-paste of
   the front/push branch. Action was always right; the description lied.

4) RENAME: `coastPush` -> `liftOffSnap`. It's counted inside the SNAP
   branch, gated on gas < 0.15 - lift-off oversteer, nothing to do with
   push. Diagnostic only, no writer reads it, but it sat in the
   experiment line under a name that pointed the wrong way.

Modules confirmed physically sound and left alone: ARB (the model the
wing fix copies), rake, toe, brake bias, differential, springs,
pressures, camber (oscillation still a known item), rear dampers
(v1.9.3), bottoming, gearing (advice-only). Front slow dampers stay on
the histogram: unlike the rear, front bump/rebound counts are near-
balanced in every real log (34/38, 106/113, 22/21), so it isn't
structurally biased, and AC's front-rebound tooltip describes a per-car
trade with no blanket rule.

Verified in test_wing_and_fast_damper.lua (28 checks) against the real
tester session and the real Ferrari/Lotus fast-damper sequences.


1.9.3: REAR DAMPER DIRECTION - the one this project got wrong the
longest, fixed on the driver's go-ahead after holding for more logs.

WHAT WAS WRONG. The slow-damper writer used a pure event-histogram: the
side with more velocity-threshold crossings is "comparatively soft", so
stiffen it. That's a damper-symmetry heuristic with no knowledge of what
the car is doing. And on the rear axle it was structurally biased -
rebound events out-number bump events in EVERY real session logged (216
vs 46, 110 vs 25, 45 vs 20), so the rear branch almost always resolved to
"stiffen rear rebound". A real tester's session (461 corners, 265
oversteer events) got rear rebound stiffened 24->28. Assetto Corsa's own
setup tooltip for that exact control says higher rear rebound makes the
car "less stable under braking and initial turn in". The app was making
a loose car looser, by design, on every Build.

THE FIX. On the rear axle the HANDLING signal now decides the direction;
the histogram is only the fallback when neither oversteer nor understeer
clearly dominates:
  LOOSE (snap > push by 25%+)  -> SOFTEN rear rebound AND rear bump
      AC: lower rear rebound = "more stable at initial turn in";
          lower rear bump = "more traction and more stability the
          moment you release the brakes"
  TIGHT (push > snap by 25%+)  -> STIFFEN rear rebound, within 30% of
                                  its limit
      AC: higher = "much more agile on slow turns that need the whole
          car to rotate" - but also less stable under braking, hence
          the headroom. Bump left alone: its tooltip effect for a
          pushing car is a trade with no clear win.
  NEITHER                       -> histogram, exactly as before
The front axle is deliberately untouched: AC's front-rebound tooltip
describes a trade (stable on fast direction change vs less understeer on
throttle but sluggish) that genuinely varies by car, and the histogram
is the honest fallback there. The bottoming override (stiffen both,
physical travel) still takes precedence over everything.

The signal is one shared function, rearHandlingSignal, used by BOTH the
REAR DAMPERS advice item and the writer, so the panel can never promise
one direction while Build does another (the exact mismatch behind the
v1.4-era "only pressure and camber got written" reports). Verified in
test_rear_rebound_direction.lua against both real tester sessions - both
flip from stiffen to soften - and against a pushing car, a mixed car
(unchanged from old behaviour) and the 25% dominance margin.

Credit where due: the driver held this position from the first session,
against the histogram logic, and was right. It took AC's own tooltip to
end the argument, and it should have been read first.

1.9.1: the baked DAMPER ranges were wrong, and v1.6.0's headline finding
with them. Corrected, and the mistake is now caught by a test.

The driver shared Assetto Corsa's own in-game damper tooltips, which quote
this car's factory defaults outright: rear rebound 26, front rebound 29,
front bump 39, rear bump 24, front fast rebound 185, front fast bump 81.
Every one sits OUTSIDE the range v1.6.0 baked (22, 22, 20, 20, 15, 22). A
car's own default cannot be out of its own range, so the baked ranges were
wrong - and so was the conclusion built on them. v1.6.0 reported that this
driver had been "pegged at maximum rear rebound for months" and that
observed values of 24-35 were all silently clamped. They weren't: 26 is
simply the default, and 24-32 are ordinary settings.

Worse, the wrong ranges did real damage rather than merely failing to
help. With fast bump baked at 0..22 against a true range of 66..88, a
Build clamped the driver's front fast bump from 88 down to 22 and the rear
from 64 to 20 - far below the legal minimum, in the name of protecting
them from values that were never out of range.

CAUSE: readSetupItem maps every SHOW_CLICKS field to a click index
0..numSteps (physical = MIN + index*STEP). These dampers instead store a
COUNT OF STEPS FROM ZERO (physical = value*STEP), so the legal stored
range is ceil(MIN/STEP)..floor(MAX/STEP) - e.g. rear rebound 11..32, which
contains the 26 default. Verified against two independent sources: all six
tooltip defaults AND every damper value observed in the driver's real
setup files (185, 101, 88, 64, 43, 34, 32 - all inside the new ranges, all
"out of range" under the old ones).

This convention is NOT universal and is deliberately NOT inferred:
lotus_exos_125_s1's dampers are click-index (proven by the live spinner API
returning [0..24] for an ini of MIN=7000 MAX=19000 STEP=500), and the
Ferrari's own TOE fields are click-index too despite sharing SHOW_CLICKS=1
with its dampers. So the rule is recorded per car, from that car's own
numbers, in gen_baked_schema.py's CONFIRMED_DAMPER_UNITS - the same
evidence-first pattern already used for camber units after over-
generalising those once.

GUARD: test_damper_ranges.lua asserts the car's own defaults and its real
observed values all fall inside the baked ranges, reading them out of this
file so it tests what ships. One invariant - a default cannot be out of
range - is enough to catch a wrong unit conversion without knowing which
conversion is right. Verified to fail against v1.6.0's numbers.

In practice this mattered less than it looks: v1.8.0 already prefers the
live spinner's own min/max over anything baked, so only sessions where
that read is unavailable ever reached these numbers.

1.8.0: Build now starts from the car's ACTUAL CURRENT SETUP instead of a
file. This is the root cause behind most of what went wrong this week.

THE PROBLEM, spotted by the driver: "any last.ini are saved on session
exit, so they dont write until i leave. To have the optimal setups
accumulate then data needs to be from what's currently set to the car."
Exactly right. Every Build nudged from findTemplateSetup's last.ini, which
AC only writes when a session ENDS - so during a session the base never
moved. Eight consecutive Builds in one real session produced byte-
identical output: ARB 30->34, ride height 24->23, toe 12->13, pressure
"base 20" every single time. Builds weren't accumulating at all; each was
the same first step re-taken. It also made unticking a module write that
stale file's value rather than what the car was running - which is how
unticking pressures produced 20psi, that car's literal MAXIMUM, on a car
the driver had been running at ~16.

THE FIX: ac.getSetupSpinners(), straight from CSP's shipped SDK, returns
every setup item as {name, label, min, max, step, value,
displayMultiplier, readOnly, units, showClicksMode} - where `name` matches
setup INI section names and `value` is what's on the car RIGHT NOW. The
live values are synced into the parsed base document in ONE place, so
every writer picks them up through the getCurVal() it already calls; no
call site changed. Five long-standing problems close together:

  1) Builds accumulate, because the base is the car, not a file.
  2) "Untick = leave it alone" is now literally true - untouched sections
     carry the LIVE value into the output.
  3) schemaLimited cars get real min/max/step for the first time, so the
     unclamped percentage-nudge path (which walked one car's rear rebound
     to 78 against a real limit of 22) is no longer reachable.
  4) Camber units stop being guesswork: displayMultiplier is the game's
     own raw->degrees factor. Its reciprocal is the scale this file spent
     three versions inferring by hand - and it reproduces the driver-
     confirmed case exactly (-3.5 deg stored as -35).
  5) No decryption needed for any of it.

ac.INIConfig.currentSetup() is deliberately NOT used: its own docs warn
that pit changes aren't reflected unless the file was saved - the same
staleness, one layer along.

SAFETY, given this replaces the core data source and cannot be verified
outside a running game: the read is pcall-guarded, every field type-
checked, and the WHOLE read is rejected unless self-consistent - if any
value sits outside its own reported min/max then those numbers aren't in
the same unit space and clamping against them would be meaningless
(precisely the trap setup.ini already sets, declaring camber MIN/MAX in
degrees while VALUE is in tenths). On rejection or unavailability the old
template path takes over unchanged. A new `liveSetup:` debug-log line
reports what came back, so ONE session settles whether this works rather
than another round of inference. Logic verified in
setupcoach-tools/acd/test_live_setup.lua (15 checks, including the guard
rejecting mixed unit spaces) - which tests the logic against an assumed
API shape and says so plainly, because a stub that encodes an assumption
is what let the v1.7.6 checkbox bug through twice.

Revert point if it goes wrong: SetupCoach_1.8.0_backup_preinstall.lua
holds v1.7.8.

first time it ran against real code: the clicked-pass check asserted
that EVERY boolean in a settings table must flip, which is wrong -
settings legitimately hold booleans that aren't checkboxes (it tripped
on a one-time migration marker). It now counts how many checkboxes were
actually drawn and asserts that exactly that many settings changed,
comparing like with like. Both guards re-verified to still fail on
deliberately broken copies afterwards.


1.7.7: THE ACTUAL CAUSE of the flashing checkbox, found by reading CSP's
own SDK definition instead of guessing a third time.

  ---@return boolean @Returns `true` if checkbox was clicked.
  function ui.checkbox(label, checked) end

ui.checkbox returns WHETHER IT WAS CLICKED - not the new value. So the
natural-looking `flag = ui.checkbox(label, flag)` sets the flag true on
the frame you click it, then false on every single frame after that.
That is precisely "tick the box, the menu flashes briefly and vanishes",
and v1.7.6's ac.storage theory was simply wrong - moving the field to a
plain engine field changed nothing because storage was never involved.
(ui.slider, by contrast, DOES return the value - "@return number
@Possibly updated slider value" - so every slider in this file was
always fine. Only checkboxes were wrong.)

ALL 17 checkbox call sites in this file had it, including FOUR that long
predate the module toggles: Show kPa, Hide OK items, Use temp analysis,
Sample in replay. Those were never noticed because they live in
windowSettings, which (v1.7.5) appears never to actually render for this
app - so their lines never ran and their stored defaults survived. The
module toggles were simply the first checkboxes this app has ever drawn
in a window that genuinely displays, which is why a long-standing bug
surfaced only now. Note the latent severity: had windowSettings ever
rendered, it would have silently forced writeDiffAeroBrake false one
frame later, quietly disabling differential/aero/brake writing.

Fixed with one local `checkbox(label, value)` helper wrapping the
documented idiom and returning the value the flag should now have, so
`flag = checkbox(label, flag)` reads naturally AND is correct; all 17
sites now call it.

TOOLING LESSON, the part worth keeping: v1.7.4 added a smoke-test stub
`checkbox = function(label, cur) return cur end` - which encoded the
WRONG assumption, so the test cheerfully validated broken code twice.
A stub that mirrors your own belief instead of the real API is worse
than no stub. smoke_test.lua now models CSP's real return semantics and
adds two regression guards, both verified to actually fail on
deliberately broken copies before being trusted: drawing the settings
window with nothing clicked must not change any persisted boolean
(catches this exact bug), and drawing it with everything clicked must
flip every one (catches the opposite - a checkbox that's dead to click).


1.7.6: v1.7.5's expand toggle itself was broken - reported immediately:
"tried to tick the box but whatever menu is supposed to be loading
flashes briefly and vanishes". `engine.showModuleToggles` (the checkbox
controlling the inline module-toggle list in windowMain) had been stored
in `settings` (an ac.storage-backed table, i.e. persisted to disk) - and
it was a BRAND NEW key with no existing value in the already-saved
settings file. The exact flash-then-vanish symptom (draws for a moment,

before the very next frame reads the field back - a class of bug this
project can't fully diagnose from outside a running game, so rather
than chase the precise ac.storage mechanism, the field was moved off
storage entirely: it's now a plain `engine.showModuleToggles` field,
same as `engine.setupMsg`/`engine.exportMsg` and other UI-only state
already in this file that never needed to survive an app restart. A
plain in-memory field can't have a storage-round-trip race at all,
regardless of what the exact underlying mechanism was.

Also worth noting for future settings additions to this app: this makes
TWO real bugs in a row from the exact same new-checkbox change (v1.7.4's
unreachable windowSettings, now this) - not because the checkbox logic
itself was wrong either time, but because both bugs live in surfaces
(CSP's settings-popup wiring, ac.storage's first-write behavior) this
project has no way to test except by shipping and waiting for a real
session's report. Worth being more conservative by default next time:
prefer plain engine fields for anything that's genuinely just UI state,
and don't assume a new persisted settings key round-trips correctly
until it's been confirmed working in an actual session.

CAUGHT BEFORE SHIPPING, worth recording since it's a real Lua trap: the

`front and settings.writeX or settings.writeY` - the classic "ternary"
idiom, and classically wrong here because the MIDDLE value is itself a
boolean. When front=true and writeX=false, `front and writeX` collapses
to false, which then falls through to `or writeY` and silently returns
writeY's value instead - exactly backwards. Caught by hand-tracing the
four true/false combinations before shipping (see
setupcoach-tools/acd/test_module_gates.lua), replaced with a plain
if/else. Worth remembering generally: `cond and a or b` is unsafe in Lua
whenever `a` can itself be false or nil.

1.7.2: v1.7.1's own diagnosis was WRONG, corrected by the user directly.
v1.7.1 treated CAMBER_LF=-24 as stale garbage because it didn't fit the
ini's literal MIN=-5/MAX=-1.2 taken as real degrees. It wasn't garbage:
the user had set that exact corner's camber themselves, and confirmed
directly - setting -3.5 degrees via Content Manager's own camber slider
produced a stored VALUE of -35, not -3.5. So -24 was always a perfectly
legitimate -2.4 degrees; this app's OWN v1.6.0/v1.7.0 baked schema had
the UNITS wrong, not the driver's setup file.

ROOT CAUSE: CAMBER_LF/RF/LR/RR are a well-known Kunos legacy quirk -
MIN/MAX/STEP in the ini describe the SLIDER's real-degree range (and
are even commented ";degrees"), but VALUE itself is stored in TENTHS of
a degree (decidegrees), a x10 mismatch the ini text never reflects.
BAKED_SETUP_SCHEMA's camber entries were baked straight from the ini's
literal numbers (min=-5,max=-1.2), so they described the wrong unit -
which is exactly why v1.7.1's own sanity check (added in good faith,
logic sound) mis-fired: -24 genuinely doesn't fit -5..-1.2 real degrees,
it only ever failed to fit because the RANGE was wrong, not the value.

FIX: BAKED_SETUP_SCHEMA's four CAMBER entries are now x10 (e.g.
CAMBER_LF: -50..-12 instead of -5..-1.2), matching VALUE's real stored
unit. This also means the runtime's own existing scale heuristic
(`schemaItem.min magnitude > 15` -> tenths-of-a-degree) now correctly
fires on its own - no separate special-casing needed at read/write time,
just the correct baked numbers. gen_baked_schema.py is fixed the same
way for any future re-bake (CAMBER_* sections now get x10 applied
automatically). v1.7.1's stale-anchor sanity check is KEPT - it's a
reasonable safety net for genuinely corrupted future data - but no
longer misfires on legitimate values now that the range it's checking
against is correct. Verified against the real session numbers in
setupcoach-tools/acd/test_camber_units.lua: -24 -> -33.5 raw (-3.35°),
-18 -> -29.4 raw (-2.94°), both sensible degree-based changes matching
the physics delta exactly, and the user's own -35 (-3.5° they set
themselves) is now correctly trusted rather than "corrected" away.

Lesson worth keeping close: v1.7.1 shipped a real, reasoned fix for a
real symptom, and was still wrong, because it trusted the ini's own
MIN/MAX comment over checking what the game/CM actually store. Direct
field evidence (the user setting a value themselves and reporting the
exact before/after) beats a documented convention every time there's a
conflict between them.


1.7.1: camber's OWN version of the same class of bug v1.6.0 fixed for
rear rebound - found by taking a driver's report seriously and checking
real files rather than the theory. Reported as "optimised setup puts
camber at max, basically zero camber, even though the advice panel
states a specific optimal angle" - and the three actual setup files
handed over as evidence proved it: the freshly-Built file had
CAMBER_LF=-5.00 (this car's real schema minimum, confirmed straight
from its own decrypted setup.ini: "MIN=-5 ;degrees"), while the two
files the driver had actually raced fastest with carried CAMBER_LF=-35 -
a number that was never valid in real degrees on any car, left over
from before camber had a real schema at all.

THE BUG: camber is the one module that computes an ABSOLUTE physics
target (the tyre's own peak-grip angle vs what it measured on track)
and adds that delta to `baseVal`, the value currently sitting in the
template file. That's fine when baseVal is trustworthy - but this
session was the FIRST time camber ever had a real schema (v1.6.0's
bake), and last.ini's CAMBER_LF was still -24, a leftover from every
session before that, all written under the OLD blind heuristic ("looks
like tenths of a degree") with no real range to check against. -24
isn't a real camber angle on this car (or any car) once you know the
true range is -5..-1.2 - but the code trusted it anyway, added a small
physics delta, and clamped: -24 + delta lands nowhere near the legal
range, so the clamp just slams it onto the boundary (-5.00), reported
as if that boundary WERE the computed answer. The advice panel's own
number (the tyre's real peak angle) never entered into what got
written at all.

THE FIX: baseVal is now sanity-checked against the real schema range
before being trusted as the anchor. When it's wildly outside (more than
a full range-width past either bound - comfortably separates "stale
garbage" from "a real value that's just near the edge"), it falls back
to the schema's own midpoint instead - the exact same fallback this
function already uses when there's no template value at all. From the
real numbers in this session (deltaDeg -0.95° for CAMBER_LF, -1.14° for
CAMBER_LR), this now writes -4.05° and -2.64° respectively - a genuine
answer near the middle of the legal range, nudged by the real computed
delta, instead of a boundary value with no connection to it. Only
affects the small number of sections (currently just camber, on the one
car with a baked schema) where the write does degrees-based ABSOLUTE
math on top of a template value - the generic percentage-nudge writer
used everywhere else (ARB, springs, dampers, etc.) already clamps
correctly with no equivalent unit-and-anchor ambiguity to get wrong.


1.7.0: "flooring" (bottoming detection) toned down, by direct request -
reaching zero bottoming flags was forcing ride height excessively high,
when a little kerb scrape is normal and expected.

TWO SEPARATE PROBLEMS, both fixed:

1) THE DETECTOR WAS TOO SENSITIVE. Bottoming fired at 92% of physical
   suspension travel, which is routine under hard braking on a stiff
   race setup and does not by itself mean the chassis touched down -
   raised to 97%, genuinely close to the packers. Worse, a pure vertical-
   G spike (>2.8, or <-0.4 the other way) counted as bottoming on its
   own, with no travel-usage check at all - so a hard kerb strike (wheel
   impact, chassis nowhere near the ground) or a crest/compression (body
   unloading, suspension nowhere near full travel) were both being
   logged as bottoming. Both G-triggers now also require travel usage
   at or above 85% on the same tick before they count; otherwise they
   fall through to the existing, consequence-free "kerb" bucket instead,
   which is what they actually were. SPRINGS' own check (95% travel,
   stiffen spring - a separate, stricter signal) was pulled out to its
   own top-level check in the process, since it used to only work by
   accident, riding inside bottoming's old lower gate.

2) BOTTOMING HAD ABSOLUTE PRIORITY OVER EVERYTHING ELSE. Any bottoming
   signal past the plain event threshold completely pre-empted rake
   advice in the SUSPENSION slot, and Build would raise ride height
   (never rake) as long as it held, with no separate, higher bar of its
   own. Introduced `bottomTh` (double the plain threshold) and gated
   ride-height raises, the SUSPENSION advice choice, and the fast-damper
   stiffen/soften flip behind it specifically - a marginal bottoming
   signal no longer locks out rake or ride-height-lowering advice for
   the rest of the session. Packer-range widening (more travel before
   the packers, zero ride-height/aero cost) deliberately stays at the
   original plain threshold - it's the cheap fix with no downside, so
   there's no reason to hold it back.

Not changed: the underlying per-session counters still only reset via
the RESET TELEMETRY button (true of every module, not particular to
bottoming) - worth hitting that between meaningfully different test runs
so old sessions' events don't keep influencing current advice.

1.4.1: a real self-cancelling bug found directly from v1.4.0's new raw
counters, on a real tester's session (ferrari_458_gt2, Interlagos,
midPush=69 and midSnap=94 both active in the same Build press):

  ARB rear (softer, less low-speed oversteer): 6 -> 5

understeer at some corners, oversteer at others, confirmed happening
here) only the larger signal by raw event count is applied, with an
explicit note about the smaller one being left for the next Build

1.0.0: the two techniques from this project's own Python prototype,
properly researched before building either - which is exactly why one
got built and the other didn't.

RAKE, built. Checked against nine independent sources (Rennlist,
SPRINGRATES, iRacing, rwmgaming, Las Motorsport, Popometer, simrace.app,
Nerdgasm, F1Race) before writing a line of code, and every one of them
agreed on the direction: more rake (front lower relative to rear)
reduces understeer; less rake increases it - through both an aero
mechanism (steeper diffuser/floor) and a plain mechanical one (raising
one end shifts weight and CG toward the other). That's about as close to
unanimous as real-world racing advice gets. Implemented as a genuine
coordinated adjustment - front and rear move in complementary directions
in the SAME pass, not the old version's single-end nudge dressed up as
rake. Tied to the HIGH-speed push/snap signal specifically, since every
source that explained why singled out cornering speed and load as what
makes rake's effect meaningful, prioritised above the old low-speed-only
branch (kept, smaller effect, direction now confirmed rather than
guessed - the "verify direction" caveat on it was never about this
concept, it's about the same per-car setup-value sign convention that
bottoming's ride-height write already carries, and carries here too).
Moves in smaller steps than an ordinary ride-height raise, since several
sources specifically warned rake's effect can be "peaky" and works
within a narrow window.

FRONT REBOUND SOFTENING FOR TURN-IN UNDERSTEER, investigated and NOT
built. This is the outcome the research process exists to produce
sometimes. Two authoritative damper-manufacturer sources gave genuinely
different answers depending on which phase of the corner they were
addressing: Koni frames added front rebound as "tightening" the car
(more understeer), while Penske frames it as helping turn-in by holding
weight on the front through the apex rather than letting it unload too
early. These aren't talking about the same symptom, and reconciling them
confidently enough to automate a real setup change felt like exactly the
kind of guess this project has already been burned by more than once.
Rake had unanimous support from nine sources; this had real, unresolved
disagreement from two of the most credible ones available. Left as a
known idea for later, not implemented on the strength of one prototype's
say-so.

4.8.2: fixes a crash that made the whole app fail to load - a total
script parse failure, not a runtime bug, so nothing could even reach the
debug log; the blank UI and the Lua console's own error message were the
only symptoms. Real-world confirmation that this needed to be shipped
fast, not theorised about.

Cause: the DCAMBER fallback lookup (4.6.0) used bare, unquoted Lua table
keys for all 102 car IDs - fine for the other 101, but the Ferrari P4/5
is genuinely named p4-5_2011 in Kunos' own car ID, and a hyphen is never
valid inside a bare Lua identifier. The parser read p4 as one token, hit
the hyphen as a minus operator, then choked trying to read 5_2011 as a
number (digits followed by letters/underscore isn't a valid Lua numeral)
- hence "malformed number near 5_2011". Since this sits in a table
constructor evaluated at load time, the entire script failed to parse,
not just this one entry - which is why the whole UI went blank rather
than one module misbehaving.

Fixed by converting every one of the 102 keys to explicit bracket-string
syntax (['p4-5_2011']=... instead of p4-5_2011=...), not just the one
broken entry - this is semantically identical at runtime but immune to
any future car ID containing a hyphen, a leading digit, or anything else
that isn't a valid bare identifier. Scanned the rest of the file for the
same bug class (any other bare table key with a hyphen) - none found.

triggered counter now records WHICH sector it fired in, not just how
often, using ac.getTrackSectorName(splinePosition) - confirmed working
via a real shipped app (Track Walker) that does exactly this in one line,
rather than parsing sections.ini by hand.

All 23 corner-triggered counters record sector data unconditionally
(slow and fast dampers both directions, bottoming, springs both axles,
both differential signals, rear toe, both brake lockup directions, both
spin/push/snap families). The advice TEXT was updated to show it for the
modules where a specific corner call is most actionable: ARB, AERO, TOE,
BRAKE, DIFFERENTIAL, and SUSPENSION's bottoming message. Damper advice
text wasn't extended to show it this round - the balance-based message
(4.6.0) already carries plenty of detail, and every damper event is
still being recorded per-sector underneath, so a later pass can surface
it there too without redoing any of the data collection.

Every part of this is additive and degrades to exactly today's behaviour
when it can't work: no sector data on a track (plenty of mod tracks
don't ship a proper sections.ini) just means the bracketed detail is
empty and the message reads exactly as it always has. debug log now
reports sectorsAvailable, which will confirm from a real session whether
this fires at all - the same pattern used for the 4.7.0 aero LUT check.


4.7.0: a full pass across the remaining modules, requested after 4.6.0's
fixes still left dampers/differential newly right but everything else
unexamined this round. One correction owed up front, three real changes.

CORRECTION: 4.6.0's changelog claimed "no telemetry sample anywhere is
filtered by track surface validity" - that was wrong, and came from a
flawed search (grepping for "surface\b" doesn't match "surfaceGrip",
since there's no word boundary between them - a bad regex, not a bad
car). Re-checked properly this time: isOnTrack() already exists, already
checks car.wheelsOutside and per-wheel surfaceGrip, and already gates
every major counter - bump/rebound, push/snap, lockup/spin, differential,
camber and mechanical-grip sampling all confirmed inside it by tracing
the actual block structure line by line. Nothing needed fixing here;
what needed fixing was the earlier claim.

1) TYRES thermal band is now compound-aware. tyreOptimumTemperature is
   already live, real, per-car data for the CENTER of the window - what
   was wrong was treating every compound as having the same WIDTH around
   that center. Real per-compound thermal curves (checked directly for
   three GT3 compounds) show the plateau is genuinely wider on a hard
   compound than a soft one: soft (70-85°C) and medium (80-95°C) are
   both ~15° windows, but hard runs 80-105°C, a ~25° window. Compounds
   with "hard" in their name now get a wider tolerance band; soft/medium
   keep the existing (already reasonably close) defaults.

2) AERO gets a real caveat instead of an unconditional "+1 click always
   helps". Unpacking real cars directly showed splitter/diffuser aero
   can be genuinely non-monotonic - the McLaren F1 GTR 96's front
   splitter peaks at 3° and is essentially stalled by 8°, and two
   different open-wheel ground-effect cars showed ride-height
   sensitivity extreme enough that one of them flips from downforce to
   lift past a certain height. A TCR car, a hot hatch, and a rally car
   with no meaningful aero showed nothing like this. The reliable
   version of this fix uses car CLASS as a conservative proxy (GT3/GTE/
   LMP/hypercar/formula get the caveat, simpler classes don't), because
   the more precise option - reading this exact car's own curve via
   ac.DataLUT11.carData and locating its actual peak - depends on an API
   confirmed to exist for PHYSICS SCRIPTS but never confirmed to work
   from APP context despite real, repeated searching. That precise
   version is still attempted as a bonus on top, fully pcall-wrapped: if
   it works, the caveat gets more specific and confident; if it doesn't,
   nothing breaks and the class-based version is what's shown. The
   debug log now records aeroLutChecked/aeroLutRisk, which will finally
   settle the app-context question one way or the other from a real
   session.

3) DIFFERENTIAL and SLOW DAMPERS (both from 4.6.0) re-verified against
   this pass rather than re-litigated - confirmed still correct on
   re-reading.

SUSPENSION assessed and left alone deliberately, not overlooked: its
"raise ride height OR stiffen springs" response to genuine bottoming is
one-directional for a legitimate physical reason - there is no real
"soften your way out of running out of travel" fix, unlike the old
damper bug where stiffening was wrong roughly as often as it was right.
The "everything says stiffen" impression from the screenshot that
started this pass traced back overwhelmingly to the damper bug (fixed in
4.6.0), not to Suspension or Springs being wrong.


4.6.0: two modules that were audited and found genuinely broken/missing,
fixed properly, plus a real expansion of the camber fallback data. This
followed a full pass across every module against real, unpacked car data
from eight cars spanning LMGT, GT3, AWD rally, two open-wheel ground-
effect cars, TCR, a hot hatch, and a classic rally car with no aero at
all - confirmed sound: pressure, ARB, packer range, fast dampers, brake
bias, springs, toe, mechanical grip. Genuinely broken: slow dampers and
differential, both fixed here.

1) SLOW DAMPERS (bump/rebound) were still using the exact "more events
   always means stiffen" logic that caused the original complaint - the
   bump:rebound balance fix was researched (the same damper-histogram
   technique behind the 4.4.0 fast-damper fix) but never actually shipped
   before this version, having been diagnosed the same session a large
   batch of car files arrived and got prioritised instead. Now uses the
   real technique: a side with MORE events is comparatively SOFTER (it
   moves more freely, crossing the velocity threshold more often), so
   restoring balance means stiffening that side or softening the other to
   match - margin-checked exactly like ARB's near-the-limit fallback.
   Events WITH bottoming on that axle override balance entirely and
   stiffen both, same as fast dampers. Worth recording: the direction was
   initially written backwards during this rebuild (softening the
   dominant side instead of stiffening it) and caught by re-deriving from
   the source before it shipped.

2) DIFFERENTIAL rebuilt from a single hedge into two distinct signals,
   each with the opposite fix, plus a real writer - this module never had
   one before. Signal A (existing): asymmetric rear slip at very low
   lateral G, nothing about cornering load to explain it - points at too
   LITTLE lock. Signal B (new): both rear wheels forced to near-equal
   slip while genuinely cornering under power, rear sliding more than
   front - a diff holding the wheels together despite the load difference
   cornering creates, which points at too MUCH lock, regardless of
   whether that shows up as exit push or snap oversteer (both are
   documented outcomes of the same over-locked cause, so the advice
   doesn't commit to just one). AWD cars are excluded outright: unpacking
   a real AWD car's data showed no DIFFERENTIAL section at all, just a
   controller chain reading GEAR/SPEED_RATIO/BRAKE through its own LUTs -
   a genuinely different system this module doesn't cover, so it says so
   rather than giving confidently wrong advice. The new writer only
   touches DIFF_POWER and DIFF_PRELOAD; DIFF_COAST is left alone since
   both signals are specifically about power-on behaviour.

3) CAMBER fallback lookup expanded from nothing to 102 real cars' DCAMBER
   coefficients (86 from a community reference table, plus 8 unpacked
   directly during this project), so the precise one-shot peak-angle
   calculation now runs on far more cars whose live tyres.ini doesn't
   expose it (CSP only hands back a WHITELIST of fields on encrypted
   cars). Cross-validated: a freshly-unpacked BMW Z4 GT3's coefficients
   matched its existing reference-table entry exactly. For the Ferrari
   458 GT2 test car specifically, this resolves to a 3.38 degree peak -
   the same number derived by hand near the start of this project, now
   computed automatically. Caveat worth keeping in mind: 7 of the 8
   newly-added cars are keyed under guessed slugs, not their real
   installed folder IDs, so those specific entries stay inert until
   corrected to match - harmless, but not yet a guaranteed win.

Known gap, not yet addressed: no telemetry sample anywhere in the app is
currently filtered by track surface validity, so off-track excursions
(grass, gravel, invalid cuts) can contaminate push/snap/lockup/bottoming/
camber counters alongside genuine on-track data. Confirmed via real
surfaces.ini files (FRICTION and IS_VALID_TRACK per surface type are
right there to check against). Flagged for the next pass.


4.5.0: a physics audit of every module, prompted by camber recommendations
showing in the UI but never reaching the setup file. Four real problems.

1) CAMBER NEVER GOT WRITTEN. The debug log showed staticCamberCaptured=
   false while every other module wrote fine. Cause: camber was the ONLY
   module that computed an ABSOLUTE target (current static + deficit), so
   it needed a live static-camber reading from a stationary pit stop.
   Everything else simply nudges the value already in your setup. Camber
   now does the same - take the stored value, move it by N clicks - so it
   writes on every run like everything else. The absolute path is still
   used when the data for it happens to be there, purely as a bonus.

2) SLOW DAMPER ADVICE WAS DRIVEN BY FAST-DAMPER DATA. AC's slow/fast
   crossover comes from DAMP_FAST_BUMPTHRESHOLD in suspensions.ini and is
   around 0.06 m/s on a real car. This app's damper event detection used
   fixed thresholds of 0.55 and 1.2 m/s - both roughly ten times ABOVE
   that crossover, so everything it called a "slow damper event" was
   already deep in the fast-damper regime. The thresholds are now read
   from the car and scaled as multiples of its own crossover, chosen so a
   typical 0.06 m/s car reproduces 0.54 / 1.2 exactly (keeping the
   calibration that has been validated on track) while a car with very
   different damping scales with it. The real value is reported in the
   debug log.

3) BUMP STOP RATE WAS THE WRONG LEVER FOR BOTTOMING. Stiffening the bump
   stop rate does not stop you reaching the bump stop - it just makes the
   hit harsher once you are on it, which costs grip rather than saving
   it. The standard answers to running out of travel are raise ride
   height, stiffen the spring, and give the suspension more room before
   the packers. The first two were already there; PACKER_RANGE is now
   used for the third, and bump stop rate is left alone.

4) ARB ONLY EVER SOFTENED. Balance depends on the RATIO of front to rear
   roll stiffness, so understeer is cured either by softening the front
   bar or stiffening the rear - the two are equivalent. Only ever
   softening meant repeated Build presses walked the flagged bar down
   toward its minimum with nothing balancing it. Now, if the bar to be
   softened is already near the bottom of its range, the opposite bar is
   stiffened instead - same balance shift, no running out of adjustment.

Modules audited and confirmed correct, for the record: toe (front toe-out
sharpens turn-in, rear toe-in adds stability, and the TOE_OUT sign
convention is handled the right way round), brake bias (front lockups ->
less front bias), wings (high-speed push -> front wing, high-speed snap ->
rear wing), springs (max travel hits -> stiffer), and pressure (delta from
the measured hot reading to the tyre's own PRESSURE_IDEAL).


4.4.0: three fixes, all from real in-game evidence.

CAMBER ADVICE WAS STUCK. The panel permanently read "looks high -> reduce
neg camber" no matter what the tyres were doing. Cause: after checking
the tread temperature spread, the code fell through to a bare angle test -
"static camber more negative than -1.15 deg is too much". Every GT car
runs -2 to -3.5 deg as standard, so that branch fired on essentially every
lap of every race car. Deleted outright: there is no universal "correct"
static camber to compare against, which is exactly why the thermal method
exists. What remains is the real trackside technique - inside-vs-outside
tread temperature of the LOADED OUTER tyre at peak corner load, target
band inside 0-12C hotter than outside - and advice is now given in CLICKS
(1 click = 0.1 deg, the common convention) sized from the measured spread
using the standard pyrometer rule of thumb of roughly 10-12C per degree
of camber, capped at 8 clicks.

CAMBER WRITER NOW WORKS ON ENCRYPTED CARS. The debug log showed
peakCamberF=n/a while tyreDataSrc=tyres.ini - i.e. the file WAS being read
(pressure targets 26.0/27.0 are not any class-matrix value) but DCAMBER_0
and DCAMBER_1 came back empty. CSP evidently exposes only a WHITELIST of
tyres.ini fields on cars with encrypted data, and the Pacejka camber
coefficients are not on it. So the writer now has two routes: the
principled DCAMBER peak-grip calculation where those coefficients are
available, and the thermal spread where they are not. Route two is pure
live telemetry, so camber now gets written on every car rather than
bailing out with "no usable DCAMBER coefficients".

FAST DAMPERS WERE BACKWARDS. Previous versions always stiffened them.
AC's own in-game description states it plainly: lower fast-bump values
let the suspension absorb more energy over bumps and kerbs, whereas a very
stiff setting means the damper barely moves, absorbing nothing and
launching the car. Suspension Secrets adds the matching rebound point -
fast rebound normally follows fast bump so the damper is extended again
in time for the next bump, and too-stiff fast rebound causes suspension
creep, each bump compressing further before full extension until it packs
down onto the bump stops. Direction now depends on WHY the fast damper is
being worked: fast events WITH bottoming -> stiffen (the travel needs
support); fast events WITHOUT bottoming -> soften (compliance over kerbs
and bumps, which is worth real mechanical grip). Both the advice text and
the setup writer follow the same rule.

Also: the duplicate SKIPPED spam is gone. The probe lists deliberately
carry both naming conventions for the same physical item (ROD_LENGTH_* vs
RIDE_HEIGHT_*, FRONT_BIAS vs BRAKE_BIAS) because cars use one or the
other; a miss on the unused name is now silent, and a genuine miss on
both is reported once instead of four times.


4.3.0: two things that should have been done several versions ago, both
pointed out correctly - the template setup file is found AUTOMATICALLY,
and camber is now real physics instead of a heuristic.

1) NO MORE "SET A BASE FILE" - the app now finds a template setup on its
   own: last.ini in the track folder, then last.ini in generic, then its
   own previous output, then (back-compat only) any name still set in
   Settings. AC rewrites last.ini every session with whatever setup was
   actually run, so in practice there is always a template available.

   Why this matters more than it sounds: a template is a plain,
   unencrypted .ini holding a real, valid, in-range value for every
   section this car supports. Once you have that, you do NOT need the
   car's data/setup.ini schema at all - you don't have to know an item's
   legal MIN/MAX/STEP if you already know a real working value to nudge
   from. That was the entire blocker on encrypted cars (the Ferrari 458
   GT2 test car being one), where every category was reporting "no
   schema range - car data likely encrypted" and writing nothing.
   Encrypted cars now write a full setup like any other.

2) CAMBER IS NOW COMPUTED, NOT GUESSED. AC's tyre model scales grip with
   inclination angle as roughly
       grip(c) = 1 + DCAMBER_0*c + DCAMBER_1*c^2      (c in radians)
   a downward parabola, so peak grip sits at
       c_peak = -DCAMBER_0 / (2 * DCAMBER_1)
   Both coefficients come straight from this car's own tyres.ini - which
   is readable EVEN ON ENCRYPTED CARS. Confirmed by the debug logs: the
   Ferrari was returning 26.0/27.0 psi targets, which are not any of the
   class-matrix fallback values, so that file was being read successfully
   all along. Same relationship the "Camber Extravaganza" app uses.
   Sanity checked on two real cars: 4.00 deg and 3.38 deg - both squarely
   in the normal range for GT slicks.

   Crucially it is NOT just "set camber to -3.4". That peak angle is what
   the tyre wants at the moment it is WORKING - at peak corner load,
   after body roll and camber gain have had their say. The app already
   measures exactly that (outer wheel camber at the highest-lateral-G
   instant of each clean corner), so:
       deficit   = -peakAngle - measuredCamberAtPeakLoad
       newStatic = currentStaticCamber + deficit
   Static camber is now only the reference point to shift FROM, never
   the thing being optimised - which is precisely what was wrong before.

   Worked example on the real test car (Ferrari 458 GT2, numbers from
   the actual debug logs): peak-grip angle 3.38 deg, loaded tyre measured
   at -2.32 deg, so a -1.06 deg deficit; static -2.06 -> -3.12 deg,
   written as VALUE=-30.26 using the 9.7x unit scale derived from the
   template. Worth noting the old heuristic was saying "reduce negative
   camber" on this exact data - the physics says the opposite.

Also: unit scale for camber is derived from the template where possible
(a -20 stored against a -2.06 deg live reading is a 9.7x scale, i.e.
tenths of a degree), with the schema range as a second opinion and raw
degrees as a last resort - and a sanity check that rejects any derived
scale that isn't near 1/10/100. The debug log now reports the template
used, the computed peak-grip angles, and per-category which route each
value took, so "why didn't X change" stays answerable from the log alone.



CRITICAL FIX - CSP's Lua Debug console caught this directly: accessing
.abs on a wheel threw 'struct_state_wheel' has no member named 'abs' -
that field doesn't exist on this CSP build's app-level wheel struct
(the changelog it was confirmed against most likely described the
physics-SCRIPT wheel struct, a different and more privileged execution
context - a lesson in not trusting a changelog across execution
contexts without stronger confirmation). Because this was an uncaught
Lua error and not just a wrong value, it silently aborted the REST of
engine:update() every single time it was hit - which meant the advice
panel (self.lastAdvice) never refreshed while the car was actually on
track, only while stationary. Everything computed BEFORE that point in
the frame (which is almost everything - bottoming, ARB, camber, lockups,
etc.) kept accumulating correctly regardless, which is why the advice
panel still looked populated; it just wasn't live. Fixed by wrapping the
per-wheel ABS read in pcall, same as every other uncertain field in this
file - this one just wasn't, and should have been.

PRESSURE REDESIGNED - the reference Python implementation computes a
setup's new pressure as `base_file_value + (target - current_reading)`:
it moves the existing, PROVEN setup value by exactly the gap between what
it's currently producing and what's wanted, using real driving data as
the anchor rather than any theory about cold/hot rise. That's more robust
than this app's previous "estimate the rise, subtract it" approach, which
depended on a fragile cold-in-the-pits capture that may never trigger in
a normal test session (confirmed happening twice in a row via the debug
log: coldPressCaptured=false both times) or on tyres.ini fields
(PRESSURE_STATIC) plenty of car mods simply don't define. Delta-from-
base-file is now the PRIMARY method whenever a base setup file is given;
the old estimated-rise approach remains as a fallback for when no base
file exists, clearly labelled as lower-confidence, since it's still
useful as a rough starting point in that case. Also (separately
researched): AC's own "predicted hot" figure in the setup screen is
typically only ~1 psi above the cold value - the much larger rises seen
under real hard driving (8+ psi) come from driving-induced heat, not
passive ambient warming, which is exactly why a real measured delta beats
a theoretical estimate here.

ADVICE TEXT MADE CONCRETE - every actionable line now states a typical
suggested increment directly (e.g. "soften front ARB (try 1 click)",
"add front toe-out (try ~0.05-0.1°)", "try +1 click front wing"),
matching the reference implementation's much more usable style, instead
of naming the direction and leaving the amount to guesswork. These are
the same ballpark numbers most real-world setup guides quote for a
single try-it step, not a value derived from this car's exact schema -
"Build Optimal Setup" still computes and writes an exact number when it
has the data to do so. AERO specifically now leads with a concrete wing
suggestion rather than only the mechanical-first reasoning, which stays
as additional context rather than the entire message. DIFFERENTIAL now
gives a concrete starting number too (-5% power lock, the single most
commonly cited first experiment for power-on rotation), while still
being honest that diff behaviour is the most drivetrain-dependent
setting here.

DEBUG LOG NOW EXPLAINS ITSELF - it previously logged raw state
(schemaLimited=true, coldPressCaptured=false) that needed interpreting.
It now also writes out, in plain language, exactly why each of
pressure/camber/everything-else-that-needs-a-base-file was or wasn't
attempted, so a look at the log should answer "why didn't X happen"
without back-and-forth. The "likely encrypted data" message was also
softened to name the real alternative honestly: an unreadable setup.ini
could equally mean this car just uses different section names than the
common ones checked for, not necessarily encryption - there's no way to
tell which from here, and both have the same fix (use a base file).

UI: the main window now shows the base setup file name and static-camber
status directly next to the Build button, since not having one of those
set is the single most common reason nothing writes beyond pressure -
previously this only surfaced after the fact, in the debug log.

IMPORTANT / limitations on "Build Optimal Setup", still true in 4.1.0:
- CSP's app-side Lua API does not expose the setup values the physics
  engine is currently running, and Assetto Corsa does not let a setup
  change take effect while the car is out on track - a new setup only
  applies the next time you leave the pits. This button writes a FILE;
  you load it from the in-game Setup screen like any other saved setup.
- It never overwrites your base file - the result is saved under a new
  name alongside it.
- A couple of sign conventions (rear toe direction on some mods, ride-
  height/rod-length on pushrod cars) vary between cars and can't be
  verified without that car's specific data. The on-screen changelog
  always shows old -> new so you can eyeball it before loading.
